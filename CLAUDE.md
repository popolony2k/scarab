# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

## Project overview

**Scarab** is a thin, game-agnostic C++17 engine layer (zlib license, matching `sunlight`'s own — see [LICENSE](LICENSE)) built on top of the **sunlight** 2D tile-map engine — hence the C++ namespace, `Scarab::*` (`Scarab::Host::EngineHost`, `Scarab::Lua::LuaEngine`, `Scarab::Engine::*`), and hence the built executable itself is named `scarab`, not after any particular game (see Build section). C++ owns only the window/render loop, resource loading, and the Lua-callable primitive API; every game built on Scarab supplies its own game logic entirely in Lua, with no C++ changes needed per game.

This repo holds Scarab's own C++ (`src/` at the repo root) and its build (the root `CMakeLists.txt` - `FetchContent`, `add_executable(scarab ...)`, everything). It contains no game content at all — a real game (for example **Caravellius**, a vertical-scrolling space shooter, in it's own separate repo) depends on Scarab via CMake `FetchContent` and supplies it's own Lua modules/resources/`project.json`. This repo was split out of a former Scarab+Caravellius monorepo (2026-08-28/29, `games/caravellius/` → `caravellius/` → this repo split out entirely, history preserved via `git filter-repo`) — `SCARAB_TODO.md` (below) tracks engine-level work seeded during that split; older history/commit messages predating the split may still describe the old monorepo layout.

`sunlight` itself is **not** in this repo — it's fetched via CMake `FetchContent` from `github.com/popolony2k/sunlight`, pinned to a tagged release via the root `CMakeLists.txt`'s own `SCARAB_SUNLIGHT_VERSION` variable (currently `0.17.2`; previously `0.17.1`, `0.17.0`, `0.16.0`, `0.15.0`, `0.14.0`, `0.13.2`, `0.13.1`, `0.13.0`, `0.12.0`, `0.11.0`, `0.10.0`, `0.9.1`, `0.9.0`, `0.8.0`, `0.7.0`, `0.6.0`, `0.5.0`, `0.4.0`, `0.3.0`, `0.2.2`, `0.2.1`, `0.2.0`, and `0.1.0` before that — bump it deliberately when sunlight cuts a new release, rather than floating on `main`). This is the *only* place that version lives — both the `FetchContent_Declare`'s own `GIT_TAG` and the `--version`/`-v` CLI output (see below) read it from this one variable, so it can't drift out of sync between what's actually fetched and what gets printed. If you need to read or modify engine internals rather than Scarab's own code, that's a separate repo; a cached checkout may exist locally under `build/_deps/sunlight-src` after a configure, and it ships its own `CLAUDE.md`.

**`SCARAB_TODO.md`** (repo root) tracks engine-level work items for Scarab (and possibly sunlight), some seeded before this repo existed on it's own.

## Build

```shell
cmake -B build -S .
cmake --build build -j 4
```

On Windows, `libxml2`/`tmx` (both fetched transitively via sunlight) link vcpkg's `iconv`/`zlib` dynamically, so `CMAKE_TOOLCHAIN_FILE` must point at vcpkg's toolchain — this is expressed as a real CMake config, not an IDE setting: `CMakePresets.json`'s `windows-vcpkg` preset (`condition`-gated on `hostSystemName == Windows`, so it's inert/invisible everywhere else) sets it from the `VCPKG_ROOT` environment variable. Configure with `cmake --preset windows-vcpkg` instead of the plain invocation above (works identically from a bare terminal, Visual Studio, CLion, or VSCode — `.vscode/settings.windows.json`'s `cmake.configurePreset` just points VSCode's CMake Tools at the same preset name, it doesn't duplicate the toolchain path). A per-OS `.vscode/settings.<os>.json` split exists (swapped into `settings.json` by the recommended `franmastromarino.vs-code-settings-os` extension) purely as VSCode-integration convenience — it must never carry `cmake.configureSettings`/cache-variable values of its own, since that was the actual bug once (a Windows session's own hand-added `CMAKE_TOOLCHAIN_FILE` in the *shared, git-tracked* `.vscode/settings.json` broke Mac/Linux configure outright, since VSCode settings have no OS conditioning — `${env:VCPKG_ROOT}` resolved to a literal, nonexistent path there). CMake itself must remain the single source of truth for anything platform-conditional.

`CMakePresets.json` also has a `default` preset (no toolchain overrides, `condition`-gated to `hostSystemName != Windows`), which exists purely to give VSCode's CMake Tools extension something to select on Mac/Linux — once *any* `CMakePresets.json` is present in a workspace, that extension switches into "a preset must be chosen" mode for its own configure UI, even though a plain CLI `cmake -B build -S .` never looks at presets at all unless you pass `--preset`. Before this preset existed, deleting `build/` and reconfiguring through VSCode on Linux/Mac hit an empty picker with no valid option but "Add new preset..." (`windows-vcpkg`'s condition filtered it out, and nothing else was defined). `.vscode/settings.linux.json`/`settings.macos.json` set `cmake.configurePreset: "default"` so the picker doesn't prompt at all in the normal case.

Debug symbols: `cmake -B build -S . -DCMAKE_C_FLAGS="-g2" -DCMAKE_CXX_FLAGS="-g2"`.

Lua backend defaults to `walterschell/Lua` (CMake-friendly). `-DSCARAB_USE_OFFICIAL_LUA_FTP=ON` switches to the official Lua 5.4.6 FTP tarball build (Unix-only).

The root `CMakeLists.txt` globs sources with `GLOB_RECURSE "src/*.cpp"` — re-run `cmake -B build -S .` after adding new `.cpp` files so the glob picks them up. (The pattern must be one combined `"src/*.cpp"` expression, not two separate arguments `"src" *.cpp` - the latter globs unscoped from `CMAKE_CURRENT_SOURCE_DIR`, which would silently sweep up `FetchContent`'d dependencies' own `.cpp` files from `build/_deps/` too if this ever ran from anywhere other than the repo root.)

The built executable **requires** a command-line argument — a `.lua` entry script path, a `.json` project file (see `EngineHost::ResolveEntryScript` below), or a single bundled `.zip` archive — and refuses to start at all without one. Run it as `./scarab project.json` (or `./scarab main.lua` directly, or `./scarab game.zip`) from the build output directory. Argument parsing is CLI11 (`FetchContent`, header-only, MIT) rather than a raw `argc`/`argv` scan — there's no C++ standard-library facility for this (POSIX `getopt` isn't available on Windows/MSVC without extra tooling, ruling it out given this project's own vcpkg/Windows support), and CLI11 already gives `--help`/usage generation and required-argument checking for free. A `--entry`/`-e <path>` option names where the project `.json` actually lives: inside a `.zip` entry (default, if omitted: `project.json` at the archive's own root; a `.lua` path there runs directly instead, no project-file indirection at all), or as an outright override of *which* `.json` to use when entry is itself a `.json` project file; combining `--entry` with a bare `.lua` entry is a usage error (`EngineHost::ResolveEntryScript` reports it as a normal fatal-error case, same as any other bad entry argument). The executable is named `scarab`, not after any specific game — which game it actually runs is determined at launch by the entry-point argument, not compiled in; naming the binary after one specific game would bake in an assumption the whole entry-point design exists to avoid.

`--version`/`-v` prints `scarab v<PROJECT_VERSION> (sunlight v<SCARAB_SUNLIGHT_VERSION>)` (e.g. `scarab v0.1.2 (sunlight v0.17.1)`) and exits, via CLI11's own `App::set_version_flag` (the same mechanism `--help` already uses — takes priority over the required `path` positional, so `./scarab --version` alone works with no other argument). Both version numbers are compiled in as string literals (`target_compile_definitions`, root `CMakeLists.txt`) from `project(scarab VERSION ...)`/`SCARAB_SUNLIGHT_VERSION` respectively — **`project(scarab VERSION ...)`'s own version must be bumped in the same commit as every new git tag** (matching sunlight's own established convention for its own `src/CMakeLists.txt`), or `--version`'s output silently goes stale relative to the tag it's actually built from.

Every resource load in this engine (Lua's `dofile`/`load_json`, texture/sound/tilemap loading, and the entry script/project-file reads themselves) routes through `SunLight::FileSystem` (mount-based, PhysFS-backed — either a loose directory or a real archive read identically; see sunlight's own `CLAUDE.md`), so a consuming project's own `.zip` bundle is fully self-contained and runs correctly from anywhere. `EngineHost::ResolveEntryScript`'s `.zip` branch mounts the archive at the exact same virtual location `LuaEngine::GetApplicationDirectory()` already exposes to Lua as `APP_DIR`, searched first — every `APP_DIR`-anchored path a consuming project's own Lua/JSON builds resolves into the archive unchanged, with zero path-construction code anywhere needing to know the difference between a loose build and an archived one.

`scarab_copy_binaries` (root `CMakeLists.txt`) copies Scarab's own runtime deps (raylib/tmx/libxml2/sunlight) into the build dir next to the executable, using `$<TARGET_FILE_DIR:scarab>` as the destination rather than `${CMAKE_CURRENT_BINARY_DIR}/$<CONFIG>/` — the latter is a real trap on a single-config generator (Unix Makefiles) where `CMAKE_BUILD_TYPE` is cached as `Debug` (making `$<CONFIG>` evaluate to `"Debug"`) but the executable itself lands with no per-config subdirectory at all, so anything copied to the `$<CONFIG>`-suffixed path silently lands somewhere the running executable never reads, while the build log still prints "Copying..."/"Built target" either way. `$<TARGET_FILE_DIR:scarab>` always resolves to wherever the executable's own output actually lands, regardless of generator/config setup. Any future custom copy target added to this build should follow the same pattern — a stray `Debug/` directory next to `build/scarab` with real-looking content but a stale executable is the tell that this bug is back.

No test suite exists for Scarab itself (`sunlight` has it's own, separate `doctest`-based suite — see it's own `CLAUDE.md`). There is no linter/formatter config; match the existing style (see below).

## CI/CD

`.github/workflows/ci.yml` — build verification only (ubuntu-latest/macos-latest/macos-15-intel/windows-latest matrix, mirroring sunlight's own `ci.yml`'s dependency-install steps), triggered on push/PR to `main`. No test step — see "No test suite exists" above. Unlike sunlight's own `ci.yml`, there's no `-DBUILD_LIBRARY_SAMPLES`/`-DBUILD_LIBRARY_TESTS` — those options don't exist here.

**macOS is covered on both architectures, deliberately** — `macos-latest` resolves to an Apple Silicon (arm64) runner image (confirmed live: `macos-26-arm64` as of this writing), so it alone would only ever build/test/release an arm64 binary. `macos-15-intel` is a real, standard GitHub-hosted runner label for genuine x86_64 hardware - confirmed live via a real throwaway workflow run (`uname -m` → `x86_64`), not assumed from docs - and isn't gated behind a paid plan; GitHub's own billing docs list "macOS 3-core or 4-core (M1 or Intel)" as a single, identically-priced SKU. **sunlight's own `release.yml` only has a single `macos-latest` entry, so sunlight's published "macos" binary is arm64-only today** - a real, live fact about a separate repo, not something fixed here.

`.github/workflows/release.yml` — triggered on `v*` tag push. Unlike sunlight's own `release.yml` (which does `cmake --install` — sunlight is a library with a real `install()` target), **Scarab has no `install()` target at all** (only a commented-out stub near the end of the root `CMakeLists.txt`) — it's an executable, not something a consumer links against, so there's nothing to "install" in the CMake sense. Packaging instead archives the built `scarab` executable together with whatever `scarab_copy_binaries` already copied next to it (raylib/tmx/libxml2/sunlight's shared libs), read directly out of the build output directory: `build/` itself on Linux/macOS (single-config Unix Makefiles, no per-config subdirectory), `build/Release/` on Windows (the multi-config Visual Studio generator GitHub's `windows-latest` runner defaults to) — see the `$<TARGET_FILE_DIR:scarab>` gotcha in the Build section above for why this split exists. Produces four platform archives: `linux-x64`, `macos-arm64`, `macos-x64`, `windows-x64` — the `runner.os == 'macOS'`-gated steps apply identically to both macOS matrix entries (`runner.os` is the OS family, not the architecture), so no extra per-arch branching was needed beyond the matrix itself. If a real `install()` target is ever added to `CMakeLists.txt`, switch `release.yml` to `cmake --install` instead (matching sunlight's own approach) rather than keeping both paths.

`.github/workflows/doxygen.yml` — generates a Doxygen HTML reference from `src/`'s own `/** @brief */` comments (see `Doxyfile`, mirroring sunlight's own) *and* runs `scripts/generate_lua_api_docs.py --format html` right after it, landing that output under `docs/doxygen/html/lua-api/` so both publish together in one deploy to GitHub Pages on push to `main` — C++ reference at `/`, Lua API reference at `/lua-api/`; also runs (build-only, no deploy) on PRs. **The Doxygen side alone is a C++ source-structure reference only — classes/methods/params — it does not and cannot know that a C++ method like `LuaSpriteApi::SetCollisionInset` is registered into Lua under a different name (`sprite_set_collision_inset`)**, since that mapping only exists inside a runtime `lua_register()`/`luaL_setfuncs()` call, not anything statically parseable; the Lua API reference is the one built specifically to document that mapping, generated straight from `@luaname`/`@luadoc`/`@luaexample` tags on each primitive's own C++ doc comment (see the Code style rule above and `scripts/generate_lua_api_docs.py`'s own module docstring for the full tag grammar) rather than hand-written separately — `docs/lua-api/README.md` is the one page still hand-written (an index with no single-primitive/class anchor to tag), also serving as that site's own landing page. `ci.yml`'s own `lua-api-docs` job runs the same generator (`--format markdown`, no arguments) as a fast, dependency-free check — it hard-fails on any registered primitive with no `@luaname` tag, so a new primitive shipped without one fails CI rather than silently missing from the published site.

### Releasing a new version

1. Bump `project(scarab VERSION ...)` in the root `CMakeLists.txt` to the new version (see the `--version` gotcha above for why this must happen — it's what `--version`/`-v` actually prints). If the change also bumps the pinned sunlight release, update `SCARAB_SUNLIGHT_VERSION` in the same commit.
2. Commit and push to `main` first (`ci.yml`/`doxygen.yml` run here; confirm `ci.yml` is green across all 4 platforms before tagging — tagging a red commit just ships the same failure via `release.yml` too).
3. Tag and push the tag: `git tag -a vX.Y.Z -m "..."` then `git push origin vX.Y.Z`. The tag is what actually triggers `release.yml` — pushing the commit to `main` alone does not.
4. Watch the run (`gh run watch <run-id>` or the Actions tab) until all 4 `package` jobs *and* the final `release` job succeed — each `package` job's own `Smoke test` step (extract the staged files to a fresh directory, run `scarab --help` from there) is what actually proves the released archive works outside the CI runner, not just that it compiled. Confirm the GitHub Release itself has all 4 assets (`gh release view vX.Y.Z`) before considering the release done — the `release` job only runs if every `package` job succeeded, so a partial matrix failure never produces a partial/broken public release.
5. **If a release run fails partway, check whether a real GitHub Release was actually published before touching the tag** (`gh release view vX.Y.Z` — `release not found` means no, since that job is gated on every `package` job succeeding). If nothing was published, it's safe to delete the tag (`git tag -d vX.Y.Z && git push origin --delete vX.Y.Z`), fix the underlying issue, and re-cut the same version number once fixed — this is exactly what happened live building the rpath fix (see the gotcha above): `v0.1.2`'s first attempt failed on Windows only, the tag was deleted with no release ever having been published, and it was re-cut clean once the Windows-specific regression was fixed. If a release *was* already published, don't delete/retag it — cut a new patch version instead, the same way `v0.17.1`→`v0.17.2` is handled on sunlight's side.

## Architecture

C++ is a thin, game-agnostic engine layer; all game logic lives in whatever game is pointed at it via the entry-point argument — this repo has no game logic in it at all.

- `src/main.cpp` — entry point. Requires a CLI11-parsed `path` positional (a `.lua` script, `.json` project file, or `.zip` bundle) plus an optional `--entry`/`-e` — CLI11 prints a usage message and exits before constructing anything if `path` is missing, so a forgotten argument never even opens a window. Builds a `SunLight::Renderer::TileMapRenderer` (window/game loop owner) and a `Scarab::Host::EngineHost` (passing both straight through), wires the latter as a tile-map listener, then `Start()`/`Run()`/`Stop()`. Also mounts the executable's own directory (`APP_DIR`) at itself *and* the process's current working directory at the virtual root — the latter exists specifically so a bare relative path (eg. `./scarab project.json`'s own relative `main_script` resolution, or any other relative path used anywhere) still resolves through `SunLight::FileSystem` exactly as plain `fopen()` always resolved it against CWD; see `EngineHost::ResolveEntryScript`'s `.zip` branch for why the `APP_DIR` mount is the one that matters for an archived build.
- `EngineHost::ResolveEntryScript` — resolves the entry-point argument to an actual Lua script path, told apart by extension. A `.json` project file (read via `nlohmann::json`, `{"main_script": "..."}`) has `main_script` resolved relative to *the project file's own directory*, not `APP_DIR` — a project should be relocatable as a whole. A bare `.lua` path is used directly. A `.zip` archive is mounted at `APP_DIR`, with `main_script` read from `project.json` at it's own root (or wherever `--entry` points inside it) — told apart by that inner path's own extension the same way the top-level entry is. There is no compiled-in default (the old `__MAIN_LUA_ENTRY_POINT_FILE` `#define` is gone) — every launch must name an entry explicitly, and a bad/missing one (including a malformed `--entry`/`.lua` combination) is a normal fatal-error case (`EngineHost::OnError`/`FatalErrorHandler`), not a silent fallback.
- `src/host/enginehost.{h,cpp}` — `EngineHost`: sound playback, the `ScriptProcessor`/`LuaEngine` wiring, the engine's own state machine (init/run-stage/fatal-error handlers), and `OnCommand` dispatch. Owns no game logic at all — `InitEngineStateHandler` just runs the entry script and transitions to `STATE_STAGE_RUNNING`; `OnCommand`'s `LOAD_STAGE_CMD`/`MOVE_SPRITES_TO_SCREEN_CMD` cases both give Lua first (and only) refusal via `LuaEngine::TryDispatchLoadStage`/`TryDispatchMoveSpritesToScreen`, calling the optional Lua globals `on_load_stage(stageId)`/`on_move_sprites_to_screen(stateId)` and reporting an error if Lua doesn't claim a valid id — there is no C++ fallback to drop to; a consuming game's own Lua code owns what a "stage" or a "wave-spawn state" even means, C++ only ferries the opaque integer id through. `CheckSpritesQueueEmpty` is the one piece of per-frame bookkeeping that isn't state-machine or Lua-dispatch — a periodic (2000ms) check that resolves `sp_wait_queue_empty()` via `LuaEngine::GetActiveEnemyCount()`. Not a collision listener — `Scarab::Engine::Lua::LuaCollisionListener` (registered by `LuaEngine::Init`) is the sole collision authority now that every sprite is Lua/`SpritePool`-owned. `sprite_add_to_layer` resolves a sprite's own layer id via sunlight's `tmx_find_layer_by_id` against the actually-loaded `.tmx`, and silently no-ops (`AddSprite` returns `false`, nothing renders, no error anywhere) if that id isn't a real layer in the currently-loaded map — which layer ids exist and what they mean is entirely up to whichever game's own Tiled maps/Lua code define them; Scarab itself has no opinion. `OnStop()` calls `m_SpritePool.Clear()`, releasing every sprite's GPU textures while the render context is still alive (see the shutdown-order gotcha below).
- `src/lua/` — the entire Lua bridge, one folder matching the `Scarab::Lua`/`Scarab::Engine::Lua` namespace nesting. `luaengine.{h,cpp}` (`Scarab::Lua::LuaEngine`) is pure orchestration: it owns the `lua_State`, wires every other class here together from `Init()`/the constructor, and keeps only the handful of methods nothing else reaches (`CallOnUpdate`, `TryDispatchMoveSpritesToScreen`/`TryDispatchLoadStage`, `GetActiveEnemyCount`, `RunFile`, which prints the actual Lua error message on failure). Everything else in this folder is `Scarab::Engine::Lua::*` — one category of Lua-callable primitive per file pair, matching `docs/lua-api/`'s own page split: `LuaScriptingApi` (`sp_wait`/`sp_clear`/`sp_wait_queue_empty`/`sp_move_sprites_to_screen`/`sp_add_label`/`sp_goto_label`/`sp_load_stage` — pure `ScriptProcessor` queue control), `LuaTimerApi` (`set_timer`/`reset_timer`), `LuaSoundApi` (`sound_*` *and*, since both are topically "Sound" even though the song forms reach `EngineHost::OnCommand` through `scriptProcessorPtr` rather than `SoundManager`, the direct/queued song commands: `play_song`/`pause_song`/`stop_song`/`resume_song` and `sp_play_song`/`sp_pause_song`/`sp_stop_song`/`sp_resume_song`), `LuaSpriteApi` (sprite CRUD + `sprite_set_animation_mode` for runtime ANIMATE_LEFT/RIGHT/CENTER switching), `LuaCameraApi`/`LuaInputApi` (incl. `input_add_gamepad`)/`LuaTilemapApi`/`LuaCollisionApi`/`LuaJsonApi`/`LuaFileSystemApi` (overrides Lua's own `dofile` to route through `SunLight::FileSystem`)/`LuaAppApi` (app-level concerns not owned by any one subsystem, e.g. `app_set_name`, `app_set_draw_fps`/`app_get_draw_fps`, `app_set_window_resizeable`/`app_get_window_resizeable`), `LuaTextApi` (font/text rendering — `set_font`/`draw_text`/`measure_text`/`screen_get_width`/`screen_get_height`; kept as it's own file rather than folded into `LuaAppApi` since text/font is it's own subsystem, not a generic app-level concern), and `LuaCollisionListener` (decodes packed handles from `Collider::GetPtrData()` — the sole collision listener in the engine). `LuaEngineUtil` is the shared-helper class every one of these depends on — `GetTileMap`/`GetSoundManager`/`GetSpritePool`/`GetScriptProcessor` (fetch the engine objects stashed as light-userdata Lua globals), `AddOneParmCommandScript` (the shared "queue a one-parameter `ScriptProcessor` command" helper `LuaScriptingApi` and `LuaSoundApi`'s queued song forms both use), `RegisterConstants`, and `s_LuaMutex` — every entry point that touches the shared `lua_State*` (both `LuaEngine`'s own methods above and `LuaTimerApi::SetTimer`'s background-thread callback) is serialized behind this one mutex, because `SunLight::Concurrent::Timer` invokes its callback on its own background thread — see "Known gotchas" below. It lives on `LuaEngineUtil`, not `LuaEngine`, specifically so `LuaTimerApi` (a separate class) can reach it too.
- `src/engine/` — deliberately **not** in the `sunlight` engine repo (see the root `CMakeLists.txt` and sunlight's own `CLAUDE.md` for that boundary). Holds `SpritePool`/`SpriteHandle` (packed generation+index handle pool, `Scarab::Engine::` namespace — no `::Lua` nesting, and neither file includes any Lua header or touches `lua_State`) — the genuinely Lua-agnostic runtime backing for every sprite any game built on Scarab creates. `Clear()` immediately destroys every slot, releasing GPU textures; must run before the window/GL context closes, see `EngineHost::OnStop` above.

## Code style (existing convention — match it, don't "fix" it)

- Scope resolution operator is always **space-padded**: `Scarab :: Host :: EngineHost`, `SunLight :: Renderer :: TileMapRenderer`, not `Scarab::Host::EngineHost`.
- Member functions/types: PascalCase (`RunStageStateHandler`, `LuaEngine`). Member variables: `m_` prefix + Hungarian-ish tags (`m_nCenterWidth` = int, `m_pMainSpritePos` = pointer, `m_str...` = string, `m_bOverride...` = bool). This convention is C++-only — the snake_case already used for every Lua-callable primitive (`sprite_configure_texture`, `tilemap_load_map`) follows the opposite, Lua-facing naming style entirely, as any consuming game's own JSON/Lua config should too.
- Struct-of-data types are prefixed `st`. Enums are UPPER_SNAKE with a type-prefixed member name (`SPRITE_MODE_CIRCULAR`) and end with a `_LAST` (and sometimes `_UNLISTED`) sentinel — keep sentinels last when extending, and watch for a sentinel that doubles as a real, meaningful value before assuming an id-assignment loop's own bound should be exclusive.
- Doxygen-style `/** @brief ... */` comments precede non-trivial methods; this repo does use them (unlike the terser default) — follow the existing pattern when touching documented methods, but don't add commentary the surrounding code doesn't already have.
- No magic numbers, project-wide — every numeric/string literal that means something gets a named constant, with a comment where the value itself needs explaining (derivation, tuning history, pointers back to an original name where relevant).
- **Whenever a new Lua-callable primitive is added to `src/lua/`, or an existing one's signature/behavior changes, add/update its `@luaname`/`@luadoc`/`@luaexample` tags (and `@luagroup`/`@luaheading` if it's part of a documented pair/group) in the same change** — the published Lua API reference (`popolony2k.github.io/scarab/lua-api/`) is generated straight from these source comments by `scripts/generate_lua_api_docs.py`, not hand-written separately, so this *is* updating the docs, not a separate step from it. `ci.yml`'s `lua-api-docs` job hard-fails on any registered primitive with no `@luaname` tag, so a genuinely missing one fails CI rather than silently shipping undocumented — but a present-but-empty/misleading tag isn't caught mechanically, so still write it like the reference it is.
- **Every `.cpp`/`.h` file under `src/` starts with the zlib license notice** (`docs/HEADER.txt`, copied verbatim as the file's first lines, one blank line before whatever comes after — a file's own `/** @brief */`-style description comment, if it has one, follows the license notice rather than replacing it) — matching `sunlight`'s own convention. Any new source file must carry it too; this is a copyright/licensing requirement, not a style nicety, so it's not optional the way most of this section is a "match existing style" convention.

## Known gotchas

- **Every entry script must queue at least one `ScriptProcessor` (`sp_*`) command before it finishes running, even if the game has nothing to sequence** — sunlight's own `ScriptProcessor::Compile()` (called once, right after the whole entry script executes, from `EngineHost::LoadLuaScript`) returns `false` if the command queue is still empty, and a failed compile is a fatal engine-startup error (`Error compiling script commands => ...`). Confirmed live building `samples/hello-world` (see `samples/`): a first version with no `sp_*` call at all failed to start with exactly that error, even though `main.lua` itself ran without error — `LuaEngine::RunFile` succeeding is not enough on its own. The fix for a game with nothing worth sequencing is a single trivial, harmless filler command (e.g. `sp_wait(1)`, a 1-millisecond non-blocking pause) purely to satisfy this requirement — there's no "queue nothing" primitive that skips it.
- `SunLight::Input::KeyboardKey` vs raylib's own global `KeyboardKey` is a real footgun in engine code (see sunlight's own `CLAUDE.md`) — always fully qualify if you touch input handling.
- `stCoordinate2D`/sprite position is top-left anchored, not center-anchored (confirmed via sunlight's own render clip rect and collision code) — a formula like `pos - height/2` doesn't mean "half a sprite-height above center", it means "half a sprite-height above the sprite's own top edge". Worth checking against before assuming any position math matches visual intuition.
- `SunLight::Concurrent::Timer::Start()` runs it's callback on it's own background thread; `lua_State` isn't thread-safe, so any code calling into Lua from both the main thread and a timer callback needs to serialize via a mutex (see `LuaEngineUtil::s_LuaMutex` — lives there, not on `LuaEngine`, since `LuaTimerApi::SetTimer`'s background-thread callback needs it too). Watch for deadlock if a mutex-holding call can trigger `Timer::Stop()` (which `std::thread::join()`s) — the timer thread must not block on the same mutex, or a `join()` from the mutex-holding thread deadlocks against it (fixed via `try_lock` in the timer callback rather than a blocking lock).
- **`s_LuaMutex` only protects the shared `lua_State*` itself — it does NOT protect `EngineHost`/`SoundManager`/raylib's own audio/engine state, which the main thread also touches every frame outside that lock.** A `set_timer` callback (background thread) that calls any Lua primitive reaching into that state — `play_song`/`sound_is_playing` (→ `SoundManager`/raylib directly), any direct-dispatch sound/song call (→ `EngineHost::OnCommand`, touching `m_CurrentSong` etc.) — races the main thread's own identical access with zero synchronization; this can corrupt state or hang the whole game if it lands inside a raylib/miniaudio-internal lock. **Rule for any `set_timer` callback**: it may only ever touch plain Lua data (safe under `s_LuaMutex`, which is all that mutex actually guarantees) — never call a primitive that reaches `EngineHost`, `SoundManager`, `SpritePool`, or any other engine-owned C++ object from inside one; flip a plain boolean flag instead and let a separate per-frame update function read/act on it the next real frame.
- **`dt`, as passed to every Lua `on_update` callback, is NOT a real measured frame time — it's a fixed `#define __FRAME_DELTA_MILLI (1000 / 60)` (`enginehost.cpp`), and that's *integer* division, truncating to `16`, not even the true `16.666...`.** Any Lua-side counter that accumulates `dt` to track real elapsed time (a timeout, a cooldown meant to correspond to real seconds) silently drifts slow against real wall-clock time by design — roughly 40ms slow per real second (~4%) from the truncation alone, compounding forever with no self-correction, and gets *worse* under real frame-rate variance (a slow frame that actually took 50ms of wall-clock time is still reported as exactly 16ms of `dt`, that difference is simply invisible to Lua). For anything tracking real elapsed time over a long, continuous duration, compare Lua's own `os.time()` (real wall-clock seconds since epoch, part of Lua's standard library) against a start timestamp directly, every frame, instead of accumulating `dt` — no accumulation error at all, since each check is against absolute real time rather than a running sum of approximations. `dt` itself remains fine for short, gameplay-feel timings (a few percent of drift over a couple of seconds is imperceptible); `os.time()` is specifically the better tool for anything longer.
- `sprite_set_active_sequence(handle, sequenceId)` unconditionally resets the target sequence's own animation state, even when it's already the active sequence — confirmed via sunlight's own source (`Sprite::SetActiveTextureSequence`, `build/_deps/sunlight-src/src/sprite/sprite.cpp`) unconditionally calling `Reset()` on the newly-selected sequence's `TextureCanvas`. Calling this every frame regardless of whether the sequence actually changed silently freezes any `AUTOMATIC_CIRCULAR`/`AUTOMATIC_RIGHT_LEFT` animation on that sequence at it's first frame forever, since the reset undoes each frame's own advance before it's ever drawn. Always track the last sequence actually set (per-sprite) and only call this again when it genuinely changes. Full primitive doc + a worked pose-following pattern are at [popolony2k.github.io/scarab/lua-api/sprite.html](https://popolony2k.github.io/scarab/lua-api/sprite.html) (or `LuaSpriteApi::SetActiveSequence`'s own doc comment in `src/lua/luaspriteapi.cpp`, which that page is generated from).
- Acquiring/positioning/`sprite_add_to_layer`-ing a sprite from a Lua module's own top-level (load-time) code fails silently and leaves it invisible, if that code runs before the map is actually loaded — a game's own entry script's `dofile`/init-style calls all happen synchronously *before* a queued `sp_load_stage` command (if any) has been dispatched, so any sprite setup at that point runs before `LoadMap` does (that only happens on the first `STATE_STAGE_RUNNING` tick that actually processes the queued stage-load). A consuming game's own modules should defer real sprite acquisition to a later, genuinely per-frame or wave-spawn-triggered hook, not top-level load-time code.
- `CMAKE_CXX_STANDARD 17` must be set **unconditionally** in the root `CMakeLists.txt`, not gated behind `if(APPLE)` — it originally was (added only for some Apple-specific raylib defines, long before this repo used `std::filesystem`). That meant Linux/GCC and Windows/MSVC builds never got an explicit standard flag and silently fell back to each compiler's own default, which can be pre-C++17 — breaking `std::filesystem` (`enginehost.cpp`'s `ResolveEntryScript`) with a confusing compile error instead of a clear "wrong standard" message. Found by actually building on Linux, not by code review — a macOS-only compile gives zero signal here. `CMAKE_CXX_STANDARD_REQUIRED ON` is set alongside it so an incompatible compiler hard-errors instead of silently downgrading again in the future.
- `EngineHost::OnStop()` must release `SpritePool`'s textures (`m_SpritePool.Clear()`) — it can't be a no-op. `TileMapRenderer::Stop()` (sunlight) calls every listener's `OnStop()` *before* `CloseWindow()` tears down the GL context, specifically so listeners get a chance to free GPU resources while the context is still valid; if `SpritePool`'s textures are instead released later, by `~SpritePool()` at program exit, that happens *after* the context is already gone — `TextureCanvas`'s destructor calling into raylib to unload a texture at that point segfaults (`rlUnloadTexture`). Symptom looks exactly like a random exit-time crash (e.g. via ESC) with no obvious connection to whatever was touched most recently — check `OnStop()`/shutdown ordering before assuming an exit crash is caused by recent unrelated changes.
- `sprite_set_pos(handle, x, y)`'s C++ binding (`LuaSpriteApi::SetPos`) reads `x`/`y` via `lua_tointeger`, which **silently fails on a genuinely fractional float** (writes 0, doesn't truncate) rather than rounding/truncating it. Any Lua-side position math should always be truncated (e.g. `math.floor`) before calling `sprite_set_pos`, even values that "shouldn't" end up fractional (e.g. an integer base plus a non-integer per-frame velocity) — skipping this doesn't error or warn, it just makes the sprite appear to silently stop moving partway (every other frame's write fails, leaving the position wherever the last successful *integer* write left it), a confusing, hard-to-diagnose symptom with no exception or log line pointing at the cause.
- **A layer's own `visible` flag in a `.tmx` gates every runtime sprite registered against that layer id too, not just it's static tile/object content — parent-child visibility, by design.** sunlight's `TileMapRenderer::DrawAllLayers` is the only path to `HandleSpriteUpdate` (the call that draws a sprite via that dispatch route), gated on `pLayer->visible` for every layer type — a sprite's own `sprite_set_visible` only ever gets a say once it's container layer is itself visible. Any map-authoring convention that uses genuinely empty placeholder object-group layers as sprite anchors must author them visible (`visible="1"`, or the attribute omitted — Tiled defaults to visible when absent), not `visible="0"`, or every sprite registered against that layer id silently never draws at all. To hide a whole layer's sprites at runtime as a group, use `tilemap_set_layer(layerId, false, ...)` (already exposed to Lua) rather than authoring the layer invisible from the start.
- **Not every C++ entry point that loads Lua actually goes through `SunLight::FileSystem` just because most do** — `LuaEngine::RunFile` (loads a game's very first script, called once from `EngineHost::LoadLuaScript`) used to use the raw C API's `luaL_dofile`, which reads via it's own internal `fopen()`, completely bypassing the mount-based filesystem layer every *other* Lua/JSON/texture/sound/tilemap load already routes through (`LuaFileSystemApi::DoFile`'s overridden `dofile` global, `LuaJsonApi::LoadJson`, `RaylibEngine`'s texture callback, `RayLibSound::Load`, `TileMapRenderer::LoadMap`). This is exactly the one call that has to succeed before an archived (`.zip`) game can even start — every other subsystem can work while the very first script inside a mounted `.zip` still can't be reached at all. Fixed to read via `IFileSystem::ReadFile` + `luaL_loadbuffer`/`lua_pcall`, mirroring `LuaFileSystemApi::DoFile`'s own pattern. If a future change adds another direct-to-`lua_State` script-loading entry point (bypassing the already-overridden `dofile` global), it needs this same treatment explicitly — routing through `SunLight::FileSystem` is not automatic just because it's the norm elsewhere in this codebase.
- **`main.cpp` mounts two separate things for two separate reasons, and both are load-bearing** — `APP_DIR` (the executable's own directory) mounted at itself, and the process's current working directory mounted at the virtual root ("/"). These aren't redundant: `EngineHost::ResolveEntryScript`'s `.json` branch deliberately resolves `main_script` *relative to the project file itself*, not `APP_DIR` (so a project stays relocatable as a whole) — for the documented normal invocation (`./scarab project.json`, a bare relative path), that produces a bare CWD-relative resolved path, which only the CWD-at-root mount can answer; the `APP_DIR`-at-itself mount only answers absolute, `APP_DIR`-prefixed virtual paths (what `.zip` entries and every `APP_DIR`-anchored Lua/JSON load actually use). Removing either mount reintroduces a real regression — a plain relative-path project launch fails with "cannot open" the moment `LuaEngine::RunFile` routes through `SunLight::FileSystem` (see the gotcha above) without the CWD mount also in place. Don't assume one of these two `Mount()` calls in `main.cpp` is dead code without re-deriving why both exist.
- **A released macOS binary that works fine on the machine that built it can still be completely broken for anyone else — "builds and runs here" is not the same as "relocatable."** Found live (2026-08-29) while dry-running a `FetchContent`-based *binary* consumption mode for a downstream project (see `caravellius`/`game-engine`'s own split-plan notes): the real `v0.1.0`/`v0.1.1` released macOS archives failed immediately once extracted anywhere outside the CI runner that built them — `dyld: Library not loaded: @rpath/libsunlight.dylib`. `otool -l` confirmed why: `scarab`'s (and `libsunlight.dylib`'s and `libtmx.*.dylib`'s) `LC_RPATH` entries were the *CI runner's own absolute build-tree paths* (`/Users/runner/work/scarab/scarab/build/_deps/...`) — CMake's default rpath is correct for running straight out of the build tree, but nothing converts that into something portable before packaging, since Scarab has no `install()` step (the build output *is* what `release.yml` ships verbatim). Fixed via `set_target_properties(scarab sunlight tmx PROPERTIES BUILD_WITH_INSTALL_RPATH TRUE INSTALL_RPATH "@loader_path")` on macOS (`"$ORIGIN"` on Linux) — `raylib`/`LibXml2` needed no fix, neither had an `LC_RPATH` entry pointing at another FetchContent'd target's build dir. **This fix alone then exposed a second, previously-masked bug**: `raylib`/`tmx`/`LibXml2` (unlike `sunlight`, which sets no `VERSION`/`SOVERSION`) each build as a real versioned file *plus* a SOVERSION symlink matching the dylib's own embedded install name (e.g. `libraylib.5.5.0.dylib` real file, `libraylib.550.dylib` symlink — what every other binary's `@rpath` reference actually looks for) — `scarab_copy_binaries` only ever copied `$<TARGET_FILE:X>` (the real, fully-versioned file), never the symlink, so the old build-tree-absolute rpath happened to paper over this by searching the *original* build directory (where the symlink still existed) instead of the flattened copy directory. Fixed by also copying `$<TARGET_SONAME_FILE:X>` for `raylib`/`tmx`/`LibXml2` (a no-op duplicate for `sunlight`, which has no separate SONAME file). **Verified via a real relocation test** — copy the flattened build output to a directory with zero connection to the original build tree, run `scarab --help` from there — both before (failed, confirming the bug) and after (succeeded) each fix. `release.yml` now runs this exact same relocation test itself (`Smoke test (Linux/macOS)`/`Smoke test (Windows)` steps, right after staging and before packaging) specifically so a regression here — or an equivalent problem on Linux/Windows that couldn't be verified locally on this one macOS dev machine — fails the release loudly instead of shipping silently broken again. **This exact class of bug is CONFIRMED (not just suspected) in `sunlight`'s own released artifacts too** (a separate repo, fix prototyped/verified in the cached `build/_deps/sunlight-src` checkout per the usual cross-repo hand-off process, not committed from here) — its `release.yml` does run a real `cmake --install` (unlike Scarab), but CMake's default `INSTALL_RPATH` target property is empty unless a project explicitly sets one, so `install()` alone doesn't automatically make a shared library's rpath portable either. Verified directly: a real `cmake --install` of sunlight's own source produced an installed `libsunlight.dylib` with **zero** `LC_RPATH` entries, and actually `dlopen()`-ing it failed immediately (`Reason: no LC_RPATH's found`) — worse than Scarab's original bug, since there was no working case at all, not even on the machine that built it. Fixed there with `set_target_properties(sunlight tmx PROPERTIES INSTALL_RPATH "@loader_path;$ORIGIN")` right before its own `install(TARGETS sunlight raylib tmx ...)` call (no `BUILD_WITH_INSTALL_RPATH` needed there, unlike Scarab — sunlight has a real `install()` step for `INSTALL_RPATH` to apply to normally) — re-verified with a real install + relocation test, load succeeded both right after install and after copying the installed files to an unrelated directory.

**A second real regression, found via the actual CI run (not caught locally, since this machine is macOS-only)**: `$<TARGET_SONAME_FILE:X>` is a **hard CMake configure-time error on Windows** — `TARGET_SONAME_FILE is not allowed for DLL target platforms` — since Windows DLLs have no SONAME/versioned-symlink concept at all. The first version of this fix broke Windows configure entirely (confirmed via a real `v0.1.2` CI run: Linux and both macOS architectures' `Smoke test` steps all passed cleanly, proving the rpath+SONAME fix genuinely works across every Unix platform tested, not just this one dev machine — but Windows failed at `Configure`, before `Build` even ran). Fixed by moving the `$<TARGET_SONAME_FILE:X>` copies out of `scarab_copy_binaries`'s main `COMMAND` list into a separate `add_custom_command(TARGET scarab_copy_binaries POST_BUILD ...)` block guarded by `if(NOT WIN32)`, mirroring this file's own existing pattern for the Windows-only Iconv/zlib DLL copies. **Lesson generalizable beyond this one bug**: a fix verified only on the one platform available locally can still break a platform that was never tested — the real CI matrix is what actually caught this, not local verification alone.
