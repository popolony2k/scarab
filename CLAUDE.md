# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

## Project overview

**Scarab** is a thin, game-agnostic C++17 engine layer (zlib license, matching `sunlight`'s own — see [LICENSE](LICENSE)) built on top of the **sunlight** 2D tile-map engine — hence the C++ namespace, `Scarab::*` (`Scarab::Host::EngineHost`, `Scarab::Lua::LuaEngine`, `Scarab::Engine::*`), and hence the built executable itself is named `scarab`, not after any particular game (see Build section). C++ owns only the window/render loop, resource loading, and the Lua-callable primitive API; every game built on Scarab supplies its own game logic entirely in Lua, with no C++ changes needed per game.

This repo holds Scarab's own C++ (`src/` at the repo root) and its build (the root `CMakeLists.txt` - `FetchContent`, `add_executable(scarab ...)`, everything). It contains no game content at all — a real game (for example **Caravellius**, a vertical-scrolling space shooter, in it's own separate repo) depends on Scarab via CMake `FetchContent` and supplies it's own Lua modules/resources/`project.json`. This repo was split out of a former Scarab+Caravellius monorepo (2026-08-28/29, `games/caravellius/` → `caravellius/` → this repo split out entirely, history preserved via `git filter-repo`) — `SCARAB_TODO.md` (below) tracks engine-level work seeded during that split; older history/commit messages predating the split may still describe the old monorepo layout.

`sunlight` itself is **not** in this repo — it's fetched via CMake `FetchContent` from `github.com/popolony2k/sunlight`, pinned to a tagged release via the root `CMakeLists.txt`'s own `SCARAB_SUNLIGHT_VERSION` variable (currently `0.38.0`; previously `0.37.0`, `0.36.0`, `0.35.0`, `0.33.1`, `0.31.0`, `0.29.0`, `0.26.1`, `0.24.0`, `0.22.0`, `0.20.0`, `0.19.0`, `0.18.1`, `0.18.0`, `0.17.3`, `0.17.2`, `0.17.1`, `0.17.0`, `0.16.0`, `0.15.0`, `0.14.0`, `0.13.2`, `0.13.1`, `0.13.0`, `0.12.0`, `0.11.0`, `0.10.0`, `0.9.1`, `0.9.0`, `0.8.0`, `0.7.0`, `0.6.0`, `0.5.0`, `0.4.0`, `0.3.0`, `0.2.2`, `0.2.1`, `0.2.0`, and `0.1.0` before that — bump it deliberately when sunlight cuts a new release, rather than floating on `main`). This is the *only* place that version lives — both the `FetchContent_Declare`'s own `GIT_TAG` and the `--version`/`-v` CLI output (see below) read it from this one variable, so it can't drift out of sync between what's actually fetched and what gets printed. If you need to read or modify engine internals rather than Scarab's own code, that's a separate repo; a cached checkout may exist locally under `build/_deps/sunlight-src` after a configure, and it ships its own `CLAUDE.md`.

**`SCARAB_TODO.md`** (repo root) tracks engine-level work items for Scarab (and possibly sunlight), some seeded before this repo existed on it's own.

## Build

```shell
cmake -B build -S .
cmake --build build -j 4
```

On Windows, `libxml2`/`tmx` (both fetched transitively via sunlight) link vcpkg's `iconv`/`zlib` dynamically, so `CMAKE_TOOLCHAIN_FILE` must point at vcpkg's toolchain — this is expressed as a real CMake config, not an IDE setting: `CMakePresets.json`'s `windows-vcpkg` preset (`condition`-gated on `hostSystemName == Windows`, so it's inert/invisible everywhere else) sets it from the `VCPKG_ROOT` environment variable. Configure with `cmake --preset windows-vcpkg` instead of the plain invocation above (works identically from a bare terminal, Visual Studio, CLion, or VSCode — `.vscode/settings.windows.json`'s `cmake.configurePreset` just points VSCode's CMake Tools at the same preset name, it doesn't duplicate the toolchain path). A per-OS `.vscode/settings.<os>.json` split exists (swapped into `settings.json` by the recommended `franmastromarino.vs-code-settings-os` extension) purely as VSCode-integration convenience — it must never carry `cmake.configureSettings`/cache-variable values of its own, since that was the actual bug once (a Windows session's own hand-added `CMAKE_TOOLCHAIN_FILE` in the *shared, git-tracked* `.vscode/settings.json` broke Mac/Linux configure outright, since VSCode settings have no OS conditioning — `${env:VCPKG_ROOT}` resolved to a literal, nonexistent path there). CMake itself must remain the single source of truth for anything platform-conditional.

`CMakePresets.json` also has a `default` preset (no toolchain overrides, `condition`-gated to `hostSystemName != Windows`), which exists purely to give VSCode's CMake Tools extension something to select on Mac/Linux — once *any* `CMakePresets.json` is present in a workspace, that extension switches into "a preset must be chosen" mode for its own configure UI, even though a plain CLI `cmake -B build -S .` never looks at presets at all unless you pass `--preset`. Before this preset existed, deleting `build/` and reconfiguring through VSCode on Linux/Mac hit an empty picker with no valid option but "Add new preset..." (`windows-vcpkg`'s condition filtered it out, and nothing else was defined). `.vscode/settings.linux.json`/`settings.macos.json` set `cmake.configurePreset: "default"` so the picker doesn't prompt at all in the normal case.

Debug symbols: `cmake -B build -S . -DCMAKE_C_FLAGS="-g2" -DCMAKE_CXX_FLAGS="-g2"`.

Lua backend defaults to `walterschell/Lua` (CMake-friendly). `-DSCARAB_USE_OFFICIAL_LUA_FTP=ON` selects an official Lua 5.4.6 FTP tarball backend instead, **but it does not currently work on any platform** (verified 2026-09-19: configure fails at `find_package(Lua REQUIRED)`, which is nested inside that option's own `else()`; no Windows/MSVC build path; never built by CI) — it is deliberately kept as the starting point for a *future*, unscheduled intent to make the official Lua the only Lua integration, which when it starts must work on macOS, Linux and Windows. The readline behavior of each backend, the verified findings and the sketched plan live in [docs/lua-integration.md](docs/lua-integration.md) — read it before touching the Lua integration in `CMakeLists.txt`.

The root `CMakeLists.txt` globs sources with `GLOB_RECURSE "src/*.cpp"` — re-run `cmake -B build -S .` after adding new `.cpp` files so the glob picks them up. (The pattern must be one combined `"src/*.cpp"` expression, not two separate arguments `"src" *.cpp` - the latter globs unscoped from `CMAKE_CURRENT_SOURCE_DIR`, which would silently sweep up `FetchContent`'d dependencies' own `.cpp` files from `build/_deps/` too if this ever ran from anywhere other than the repo root.)

The built executable **requires** a command-line argument — a `.lua` entry script path, a `.json` project file (see `EngineHost::ResolveEntryScript` below), or a single bundled `.zip` archive — and refuses to start at all without one. Run it as `./scarab project.json` (or `./scarab main.lua` directly, or `./scarab game.zip`) from the build output directory. Argument parsing is CLI11 (`FetchContent`, header-only, MIT) rather than a raw `argc`/`argv` scan — there's no C++ standard-library facility for this (POSIX `getopt` isn't available on Windows/MSVC without extra tooling, ruling it out given this project's own vcpkg/Windows support), and CLI11 already gives `--help`/usage generation and required-argument checking for free. A `--entry`/`-e <path>` option names where the project `.json` actually lives: inside a `.zip` entry (default, if omitted: `project.json` at the archive's own root; a `.lua` path there runs directly instead, no project-file indirection at all), or as an outright override of *which* `.json` to use when entry is itself a `.json` project file; combining `--entry` with a bare `.lua` entry is a usage error (`EngineHost::ResolveEntryScript` reports it as a normal fatal-error case, same as any other bad entry argument). The executable is named `scarab`, not after any specific game — which game it actually runs is determined at launch by the entry-point argument, not compiled in; naming the binary after one specific game would bake in an assumption the whole entry-point design exists to avoid.

`--version`/`-v` prints `scarab v<PROJECT_VERSION> (sunlight v<SCARAB_SUNLIGHT_VERSION>, <Lua release>)` (e.g. `scarab v0.1.25 (sunlight v0.38.0, Lua 5.4.7)`) and exits, via CLI11's own `App::set_version_flag` (the same mechanism `--help` already uses — takes priority over the required `path` positional, so `./scarab --version` alone works with no other argument). The Scarab/sunlight version numbers are compiled in as string literals (`target_compile_definitions`, root `CMakeLists.txt`) from `project(scarab VERSION ...)`/`SCARAB_SUNLIGHT_VERSION` respectively — **`project(scarab VERSION ...)`'s own version must be bumped in the same commit as every new git tag** (matching sunlight's own established convention for its own `src/CMakeLists.txt`), or `--version`'s output silently goes stale relative to the tag it's actually built from. The Lua release string is different — not a Scarab-owned define at all, but read directly from Lua's own `LUA_RELEASE` compile-time macro (`lua.h`, transitively included via `lua/luaengine.h`), deliberately never hand-copied into a CMake variable of its own: the default Lua backend (`walterschell/Lua`, `GIT_TAG master`) tracks whatever Lua release that fork currently packages, not a version pinned anywhere in this repo — confirmed live to actually be `5.4.7`, while the *alternate* backend (`SCARAB_USE_OFFICIAL_LUA_FTP`) is hardcoded to `5.4.6` in its own URL. Reading `LUA_RELEASE` straight from whichever `lua.h` actually got compiled against keeps this accurate for either backend automatically, with no separate tracking needed.

Every resource load in this engine (Lua's `dofile`/`load_json`, texture/sound/tilemap loading, and the entry script/project-file reads themselves) routes through `SunLight::FileSystem` (mount-based, PhysFS-backed — either a loose directory or a real archive read identically; see sunlight's own `CLAUDE.md`), so a consuming project's own `.zip` bundle is fully self-contained and runs correctly from anywhere. `EngineHost::ResolveEntryScript`'s `.zip` branch mounts the archive at the exact same virtual location `LuaEngine::GetApplicationDirectory()` already exposes to Lua as `APP_DIR`, searched first — every `APP_DIR`-anchored path a consuming project's own Lua/JSON builds resolves into the archive unchanged, with zero path-construction code anywhere needing to know the difference between a loose build and an archived one.

`scarab_copy_binaries` (root `CMakeLists.txt`) copies Scarab's own runtime deps (raylib/tmx/libxml2/sunlight) into the build dir next to the executable, using `$<TARGET_FILE_DIR:scarab>` as the destination rather than `${CMAKE_CURRENT_BINARY_DIR}/$<CONFIG>/` — the latter is a real trap on a single-config generator (Unix Makefiles) where `CMAKE_BUILD_TYPE` is cached as `Debug` (making `$<CONFIG>` evaluate to `"Debug"`) but the executable itself lands with no per-config subdirectory at all, so anything copied to the `$<CONFIG>`-suffixed path silently lands somewhere the running executable never reads, while the build log still prints "Copying..."/"Built target" either way. `$<TARGET_FILE_DIR:scarab>` always resolves to wherever the executable's own output actually lands, regardless of generator/config setup. Any future custom copy target added to this build should follow the same pattern — a stray `Debug/` directory next to `build/scarab` with real-looking content but a stale executable is the tell that this bug is back.

No test suite exists for Scarab itself (`sunlight` has it's own, separate `doctest`-based suite — see it's own `CLAUDE.md`). There is no linter/formatter config; match the existing style (see below).

## CI/CD

`.github/workflows/ci.yml` — build verification only (ubuntu-latest/macos-latest/macos-15-intel/windows-latest matrix, mirroring sunlight's own `ci.yml`'s dependency-install steps), triggered on push/PR to `main`. No test step — see "No test suite exists" above. Unlike sunlight's own `ci.yml`, there's no `-DBUILD_LIBRARY_SAMPLES`/`-DBUILD_LIBRARY_TESTS` — those options don't exist here.

**macOS is covered on both architectures, deliberately** — `macos-latest` resolves to an Apple Silicon (arm64) runner image (confirmed live: `macos-26-arm64` as of this writing), so it alone would only ever build/test/release an arm64 binary. `macos-15-intel` is a real, standard GitHub-hosted runner label for genuine x86_64 hardware - confirmed live via a real throwaway workflow run (`uname -m` → `x86_64`), not assumed from docs - and isn't gated behind a paid plan; GitHub's own billing docs list "macOS 3-core or 4-core (M1 or Intel)" as a single, identically-priced SKU. **sunlight's own `release.yml` only has a single `macos-latest` entry, so sunlight's published "macos" binary is arm64-only today** - a real, live fact about a separate repo, not something fixed here.

`.github/workflows/release.yml` — triggered on `v*` tag push. Unlike sunlight's own `release.yml` (which does `cmake --install` — sunlight is a library with a real `install()` target), **Scarab has no `install()` target at all** (only a commented-out stub near the end of the root `CMakeLists.txt`) — it's an executable, not something a consumer links against, so there's nothing to "install" in the CMake sense. Packaging instead archives the built `scarab` executable together with whatever `scarab_copy_binaries` already copied next to it (raylib/tmx/libxml2/sunlight's shared libs), read directly out of the build output directory: `build/` itself on Linux/macOS (single-config Unix Makefiles, no per-config subdirectory), `build/Release/` on Windows (the multi-config Visual Studio generator GitHub's `windows-latest` runner defaults to) — see the `$<TARGET_FILE_DIR:scarab>` gotcha in the Build section above for why this split exists. Produces four platform archives: `linux-x64`, `macos-arm64`, `macos-x64`, `windows-x64` — the `runner.os == 'macOS'`-gated steps apply identically to both macOS matrix entries (`runner.os` is the OS family, not the architecture), so no extra per-arch branching was needed beyond the matrix itself. If a real `install()` target is ever added to `CMakeLists.txt`, switch `release.yml` to `cmake --install` instead (matching sunlight's own approach) rather than keeping both paths.

Each `package` job's own `Configure` step also derives a fresh `SCARAB_CONTENT_KEY` for that release — `HMAC-SHA256(the SCARAB_RELEASE_KEY_SALT repo secret, that release's own tag name)` via `python3`/`python` (verified present on all 3 runner OSes beforehand; Windows only guarantees `python` on `PATH`, not `python3`) — and passes `-DSCARAB_CONTENT_KEY_IS_SHARED=ON` alongside it, so every official release binary prints the README's own "AS-IS" runtime warning (see the `src/main.cpp` bullet above). Deterministic given the same salt+tag, so all 4 platform jobs of one release independently compute the identical key with zero cross-job coordination, yet it still changes release to release — see README.md's own "Content encryption" section for the full "why," not just "how." A dedicated `Verify SCARAB_CONTENT_KEY actually configured` step right after each `Configure` step checks the cached value's own *length* only (64 hex chars expected) — `release.yml` has no test/run step that would otherwise prove the derivation actually worked (a silently-empty key builds identically to a real one, no visible difference in the log either way) — and the computed key itself is registered via `::add-mask::` for log redaction, since GitHub only auto-masks the literal registered secret (the salt), not a value derived from it. `ci.yml`'s own `Configure` steps do the equivalent for build verification only, using a separate, simpler repo secret (`SCARAB_CI_CONTENT_KEY`, a fixed throwaway value, not derived/rotated) — deliberately never reused for `release.yml`, since anything `ci.yml` builds is discarded, never published.

`.github/workflows/doxygen.yml` — generates a Doxygen HTML reference from `src/`'s own `/** @brief */` comments (see `Doxyfile`, mirroring sunlight's own) *and* runs `scripts/generate_lua_api_docs.py --format html` right after it, landing that output under `docs/doxygen/html/lua-api/` so both publish together in one deploy to GitHub Pages on push to `main` — C++ reference at `/`, Lua API reference at `/lua-api/`; also runs (build-only, no deploy) on PRs. **The Doxygen side alone is a C++ source-structure reference only — classes/methods/params — it does not and cannot know that a C++ method like `LuaSpriteApi::SetCollisionInset` is registered into Lua under a different name (`sprite_set_collision_inset`)**, since that mapping only exists inside a runtime `lua_register()`/`luaL_setfuncs()` call, not anything statically parseable; the Lua API reference is the one built specifically to document that mapping, generated straight from `@luaname`/`@luadoc`/`@luaexample` tags on each primitive's own C++ doc comment (see the Code style rule above and `scripts/generate_lua_api_docs.py`'s own module docstring for the full tag grammar) rather than hand-written separately — `docs/lua-api/README.md` is the one page still hand-written (an index with no single-primitive/class anchor to tag), also serving as that site's own landing page. `ci.yml`'s own `lua-api-docs` job runs the same generator (`--format markdown`, no arguments) as a fast, dependency-free check — it hard-fails on any registered primitive with no `@luaname` tag, so a new primitive shipped without one fails CI rather than silently missing from the published site.

### Releasing a new version

1. Bump `project(scarab VERSION ...)` in the root `CMakeLists.txt` to the new version (see the `--version` gotcha above for why this must happen — it's what `--version`/`-v` actually prints). If the change also bumps the pinned sunlight release, update `SCARAB_SUNLIGHT_VERSION` in the same commit.
2. Commit and push to `main` first (`ci.yml`/`doxygen.yml` run here; confirm `ci.yml` is green across all 4 platforms before tagging — tagging a red commit just ships the same failure via `release.yml` too).
3. Tag and push the tag: `git tag -a vX.Y.Z -m "..."` then `git push origin vX.Y.Z`. The tag is what actually triggers `release.yml` — pushing the commit to `main` alone does not.
4. Watch the run (`gh run watch <run-id>` or the Actions tab) until all 4 `package` jobs *and* the final `release` job succeed — each `package` job's own `Smoke test` step (extract the staged files to a fresh directory, run `scarab --help` from there) is what actually proves the released archive works outside the CI runner, not just that it compiled. Confirm the GitHub Release itself has all 4 assets (`gh release view vX.Y.Z`) before considering the release done — the `release` job only runs if every `package` job succeeded, so a partial matrix failure never produces a partial/broken public release.
5. **If a release run fails partway, check whether a real GitHub Release was actually published before touching the tag** (`gh release view vX.Y.Z` — `release not found` means no, since that job is gated on every `package` job succeeding). If nothing was published, it's safe to delete the tag (`git tag -d vX.Y.Z && git push origin --delete vX.Y.Z`), fix the underlying issue, and re-cut the same version number once fixed — this is exactly what happened live building the rpath fix (see the gotcha above): `v0.1.2`'s first attempt failed on Windows only, the tag was deleted with no release ever having been published, and it was re-cut clean once the Windows-specific regression was fixed. If a release *was* already published, don't delete/retag it — cut a new patch version instead, the same way `v0.17.1`→`v0.17.2` is handled on sunlight's side.

## Architecture

C++ is a thin, game-agnostic engine layer; all game logic lives in whatever game is pointed at it via the entry-point argument — this repo has no game logic in it at all.

- `src/main.cpp` — entry point. Requires a CLI11-parsed `path` positional (a `.lua` script, `.json` project file, or `.zip` bundle) plus an optional `--entry`/`-e` — CLI11 prints a usage message and exits before constructing anything if `path` is missing, so a forgotten argument never even opens a window. A separate `--pack <config.json>` mode (mutually exclusive with `path`/`--entry`) runs the content-encryption packaging tool (`tools/pack.lua`, copied next to the built executable by `scarab_copy_binaries`) headlessly from any directory — no window opens; see `README.md`'s own "Content encryption" section and `tools/README.md`. A `--headless` mode (mutually exclusive with `--pack`; takes the normal entry-point positional) builds the renderer with `RENDERER_BACKEND_NULL` (sunlight v0.26.1+'s null backend — no window/GPU, real audio, null input that reads "nothing pressed", texture sizes parsed from PNG/JPEG headers) and calls `EngineHost::UseVirtualTime()` right after construction, which replaces Lua's own `os.time`/`os.clock` with virtual-clock versions (`LuaAppApi::InstallVirtualClock`; `os.time(table)` still forwards to the real one). `--fast` (`FRAME_PACING_UNLIMITED`), `--max-frames N` (`RendererConfig::nMaxFrames`) and `--max-frames-ok` all require `--headless`: a budget-ended run leaves `GetExitRequested()` false, which is how `main()` tells it from `app_quit()` — only unambiguous on the null window, which can't be closed by a user, hence the requirement — and exits `EXIT_FRAME_BUDGET_EXHAUSTED` (3, `main.h`) unless `--max-frames-ok`. Fatal engine/Lua errors already `exit(EXIT_FAILURE)` from `EngineHost::FatalErrorHandler` in every mode. See README.md's "Headless mode". Right after the required-arg check, unconditionally prints a runtime warning to stderr — on *every* invocation, both `--pack` and the normal windowed path — if `SCARAB_CONTENT_KEY_IS_SHARED` (a separate compile-time flag from `SCARAB_CONTENT_KEY` itself, set only by `release.yml`) is `1`, restating README.md's own "AS-IS" disclosure live at the point of use rather than only in a doc someone could skip past; silent on any build with no key or a real private one. Does **not** create the renderer up front any more (Scarab v0.1.21 groundwork): a `Scarab::Host::RendererProvider` owns the process's one `SunLight::Renderer::TileMapRenderer` and creates it on demand — either the default (`MakeDefaultRendererConfig()` fills a `RendererConfig` from `main.h`'s `DISPLAY_*`/`VIEWPORT_*`/etc. defaults) the first time a primitive needs a window or when the entry script finishes without needing one, or (once `renderer_create` exists) explicitly. Creation goes through sunlight v0.24.0's checked `TileMapRenderer::Create(RendererConfig, &err)` — a config that can't work (eg. a backend this sunlight build lacks) is a clean error — and the provider `Start()`s the renderer immediately, so its window is open the moment it exists (load-time code like `set_font` keeps working). `--headless` is applied by the provider to whichever renderer it creates (null backend forced, the command line's `--fast`/`--max-frames` win). `main()` builds the provider and a `Scarab::Host::EngineHost` (passing the provider; the host registers itself as tile-map listener via the provider's created-hook), then calls `EngineHost::RunEntryScript()` **before any window exists** (a fatal script error exits right there, no window ever having opened), `RendererProvider::EnsureCreated()`, and `Run()`/`Stop()` on the renderer. This is step 2 of the Lua-owned-renderer-lifecycle work (see sunlight's `RendererConfig`/`IWindow`): behavior-neutral by design — verified identical against the pre-refactor binary via a probe script printing every renderer setting Lua can observe (screen/viewport/zoom/draw-fps/resizeable/exit-key/target-fps/stretch/fullscreen). `app_set_fullscreen`'s strategy enum and the `FULLSCREEN_STRATEGY_*` Lua constants use `SunLight::Window::FullscreenStrategy` (moved there in sunlight v0.24.0; the old `IEngine::` spellings only survive as aliases). Registers `LuaCryptoApi::TryDecryptBytes` as `SunLight::FileSystem::IFileSystem::SetReadFilter`'s callback (sunlight v0.18.0+) *before* any `Mount()` call, so every read sunlight itself performs (textures/sounds/tilemaps) transparently decrypts content-encrypted assets the same way Scarab's own read paths already do — a no-op, byte-identical to today's behavior, when this build has no `SCARAB_CONTENT_KEY` configured. Also mounts the executable's own directory (`APP_DIR`) at itself *and* the process's current working directory at the virtual root — the latter exists specifically so a bare relative path (eg. `./scarab project.json`'s own relative `main_script` resolution, or any other relative path used anywhere) still resolves through `SunLight::FileSystem` exactly as plain `fopen()` always resolved it against CWD; see `EngineHost::ResolveEntryScript`'s `.zip` branch for why the `APP_DIR` mount is the one that matters for an archived build.
- `EngineHost::ResolveEntryScript` — resolves the entry-point argument to an actual Lua script path, told apart by extension. A `.json` project file (read via `nlohmann::json`, `{"main_script": "..."}`) has `main_script` resolved relative to *the project file's own directory*, not `APP_DIR` — a project should be relocatable as a whole. A bare `.lua` path is used directly. A `.zip` archive is mounted at `APP_DIR`, with `main_script` read from `project.json` at it's own root (or wherever `--entry` points inside it) — told apart by that inner path's own extension the same way the top-level entry is. There is no compiled-in default (the old `__MAIN_LUA_ENTRY_POINT_FILE` `#define` is gone) — every launch must name an entry explicitly, and a bad/missing one (including a malformed `--entry`/`.lua` combination) is a normal fatal-error case (`EngineHost::OnError`/`FatalErrorHandler`), not a silent fallback.
- `src/host/enginehost.{h,cpp}` — `EngineHost`: sound playback, the `ScriptProcessor`/`LuaEngine` wiring, the engine's own state machine (init/run-stage/fatal-error handlers), and `OnCommand` dispatch. Owns no game logic at all — `InitEngineStateHandler` just runs the entry script and transitions to `STATE_STAGE_RUNNING`; `OnCommand`'s `LOAD_STAGE_CMD`/`MOVE_SPRITES_TO_SCREEN_CMD` cases both give Lua first (and only) refusal via `LuaEngine::TryDispatchLoadStage`/`TryDispatchMoveSpritesToScreen`, calling the optional Lua globals `on_load_stage(stageId)`/`on_move_sprites_to_screen(stateId)` and reporting an error if Lua doesn't claim a valid id — there is no C++ fallback to drop to; a consuming game's own Lua code owns what a "stage" or a "wave-spawn state" even means, C++ only ferries the opaque integer id through. `CheckSpritesQueueEmpty` is the one piece of per-frame bookkeeping that isn't state-machine or Lua-dispatch — a periodic (2000ms) check that resolves `sp_wait_queue_empty()` via `LuaEngine::GetActiveEnemyCount()`. Not a collision listener — `Scarab::Engine::Lua::LuaCollisionListener` (registered by `LuaEngine::Init`) is the sole collision authority now that every sprite is Lua/`SpritePool`-owned. `sprite_add_to_layer` resolves a sprite's own layer id via sunlight's `tmx_find_layer_by_id` against the actually-loaded `.tmx`, and silently no-ops (`AddSprite` returns `false`, nothing renders, no error anywhere) if that id isn't a real layer in the currently-loaded map — which layer ids exist and what they mean is entirely up to whichever game's own Tiled maps/Lua code define them; Scarab itself has no opinion. `OnStop()` calls `m_SpritePool.Clear()`, releasing every sprite's GPU textures while the render context is still alive (see the shutdown-order gotcha below).
- `src/lua/` — the entire Lua bridge, one folder matching the `Scarab::Lua`/`Scarab::Engine::Lua` namespace nesting. `luaengine.{h,cpp}` (`Scarab::Lua::LuaEngine`) is pure orchestration: it owns the `lua_State`, wires every other class here together from `Init()`/the constructor, and keeps only the handful of methods nothing else reaches (`CallOnUpdate`, `TryDispatchMoveSpritesToScreen`/`TryDispatchLoadStage`, `GetActiveEnemyCount`, `RunFile`, which prints the actual Lua error message on failure). Everything else in this folder is `Scarab::Engine::Lua::*` — one category of Lua-callable primitive per file pair, matching `docs/lua-api/`'s own page split: `LuaScriptingApi` (`sp_wait`/`sp_clear`/`sp_wait_queue_empty`/`sp_move_sprites_to_screen`/`sp_add_label`/`sp_goto_label`/`sp_load_stage` — pure `ScriptProcessor` queue control), `LuaTimerApi` (`set_timer`/`reset_timer`), `LuaSoundApi` (`sound_*` *and*, since both are topically "Sound" even though the song forms reach `EngineHost::OnCommand` through `scriptProcessorPtr` rather than `SoundManager`, the direct/queued song commands: `play_song`/`pause_song`/`stop_song`/`resume_song` and `sp_play_song`/`sp_pause_song`/`sp_stop_song`/`sp_resume_song`), `LuaSpriteApi` (sprite CRUD + `sprite_set_animation_mode` for runtime ANIMATE_LEFT/RIGHT/CENTER switching), `LuaCameraApi`/`LuaInputApi` (incl. `input_add_gamepad`)/`LuaTilemapApi`/`LuaCollisionApi`/`LuaJsonApi`/`LuaFileSystemApi` (overrides Lua's own `dofile` to route through `SunLight::FileSystem`)/`LuaAppApi` (app-level concerns not owned by any one subsystem, e.g. `app_set_name`, `app_set_draw_fps`/`app_get_draw_fps`, `app_set_window_resizeable`/`app_get_window_resizeable`, `app_quit` — the first programmatic way to close the game at all, sunlight v0.19.0+'s `IDrawSurface::RequestExit`; `app_set_exit_key`/`app_get_exit_key` — which key (default `KEY_ESCAPE`, `KEY_NULL` to disable) triggers that same behavior on its own, sunlight v0.20.0+'s `IDrawSurface::SetExitKey`/`GetExitKey`; `app_get_time` — real, monotonic wall-clock seconds (fractional, sub-millisecond) since window init, sunlight v0.22.0+'s `IDrawSurface::GetElapsedTime`, the sub-second real-time source Lua otherwise lacks — `os.time()` is whole-second only and `dt` is a fixed non-measured value, see the `dt` gotcha below; only meaningful once the window exists, so call it from `on_update` or later, not top-level load-time code), `LuaRendererApi` (`renderer_create`/`renderer_destroy`/`renderer_get_current`/`renderer_get_config`/`renderer_get_default_view`/`renderer_get_backend`/`renderer_get_view_count`, plus the `RENDERER_BACKEND_*`/`VIEW_CONTROL_MODE_*`/`FRAME_PACING_*`/`ZOOM_*` constants — the Lua way to create the process's one renderer with your own settings instead of Scarab's defaults; goes through `IRendererProvider`, needs no renderer itself, and is registered from `LuaEngine::Init`; see its own gotcha below for the ordering rule and the strictness), `LuaViewApi` (the view-addressed `view_*` functions — `view_set_zoom`/`get_zoom`, `view_set_preferred_zoom`/`get_`, `view_set_zoom_limits`/`get_`, `view_set_zoom_enabled`/`get_`, `view_zoom_in`/`out`/`reset`, `view_set_dimension`/`get_`, `view_set_scroll_step`/`get_`, `view_set_camera_position`/`get_`, `view_move_camera_*`, `view_reset_camera`, `view_create`/`view_destroy` (real extra views since v0.1.23), `view_set_visible`/`get_`, `view_set_draw_order`/`get_`, `view_set_clear_background`/`get_`, `view_set_background_color`/`view_use_map_background_color`, `view_show_layer`/`view_show_only_layers`/`view_show_all_layers`/`view_is_layer_shown`, `view_fit_to_map`; takes a view id first — an opaque integer, `0` = the renderer's default view, the one the older global `camera_*`/`zoom_*`/`viewport_*` act on — and reports every failure as `nil, "message"`), `LuaTextApi` (font/text rendering — `set_font`/`draw_text`/`measure_text`/`screen_get_width`/`screen_get_height`; kept as it's own file rather than folded into `LuaAppApi` since text/font is it's own subsystem, not a generic app-level concern), `LuaCryptoApi` (`crypto_encrypt_data`/`crypto_decrypt_data` — content encryption via libsodium, keyed by the compile-time `SCARAB_CONTENT_KEY`, never a Lua-supplied value; see `README.md`'s own "Content encryption" section), `LuaPackApi` (`pack_list_directory`/`pack_read_file`/`pack_write_file`/`pack_create_archive`/`pack_add_entry`/`pack_close_archive` — miniz-backed `.zip` writing for `tools/pack.lua`, the content-encryption packaging tool; deliberately the one `src/lua/` file whose primitives read/write real native OS paths rather than routing through `SunLight::FileSystem`, since packaging runs against a loose source tree before any mounting concept applies — see `tools/README.md`), and `LuaCollisionListener` (decodes packed handles from `Collider::GetPtrData()` — the sole collision listener in the engine). `LuaEngineUtil` is the shared-helper class every one of these depends on — `GetTileMap`/`GetSoundManager`/`GetSpritePool`/`GetScriptProcessor` (fetch the engine objects stashed as light-userdata Lua globals), `AddOneParmCommandScript` (the shared "queue a one-parameter `ScriptProcessor` command" helper `LuaScriptingApi` and `LuaSoundApi`'s queued song forms both use), `RegisterConstants`, and `s_LuaMutex` — every entry point that touches the shared `lua_State*` (both `LuaEngine`'s own methods above and `LuaTimerApi::SetTimer`'s background-thread callback) is serialized behind this one mutex, because `SunLight::Concurrent::Timer` invokes its callback on its own background thread — see "Known gotchas" below. It lives on `LuaEngineUtil`, not `LuaEngine`, specifically so `LuaTimerApi` (a separate class) can reach it too.
- `src/engine/` — deliberately **not** in the `sunlight` engine repo (see the root `CMakeLists.txt` and sunlight's own `CLAUDE.md` for that boundary). Holds `SpritePool`/`SpriteHandle` (packed generation+index handle pool, `Scarab::Engine::` namespace — no `::Lua` nesting, and neither file includes any Lua header or touches `lua_State`) — the genuinely Lua-agnostic runtime backing for every sprite any game built on Scarab creates. `Clear()` immediately destroys every slot, releasing GPU textures; must run before the window/GL context closes, see `EngineHost::OnStop` above.

## Code style (existing convention — match it, don't "fix" it)

- Scope resolution operator is always **space-padded**: `Scarab :: Host :: EngineHost`, `SunLight :: Renderer :: TileMapRenderer`, not `Scarab::Host::EngineHost`.
- Member functions/types: PascalCase (`RunStageStateHandler`, `LuaEngine`). Member variables: `m_` prefix + Hungarian-ish tags (`m_nCenterWidth` = int, `m_pMainSpritePos` = pointer, `m_str...` = string, `m_bOverride...` = bool). This convention is C++-only — the snake_case already used for every Lua-callable primitive (`sprite_configure_texture`, `tilemap_load_map`) follows the opposite, Lua-facing naming style entirely, as any consuming game's own JSON/Lua config should too.
- Struct-of-data types are prefixed `st`. Enums are UPPER_SNAKE with a type-prefixed member name (`SPRITE_MODE_CIRCULAR`) and end with a `_LAST` (and sometimes `_UNLISTED`) sentinel — keep sentinels last when extending, and watch for a sentinel that doubles as a real, meaningful value before assuming an id-assignment loop's own bound should be exclusive.
- Doxygen-style `/** @brief ... */` comments precede non-trivial methods; this repo does use them (unlike the terser default) — follow the existing pattern when touching documented methods, but don't add commentary the surrounding code doesn't already have.
- No magic numbers, project-wide — every numeric/string literal that means something gets a named constant, with a comment where the value itself needs explaining (derivation, tuning history, pointers back to an original name where relevant).
- **Whenever a new Lua-callable primitive is added to `src/lua/`, or an existing one's signature/behavior changes, add/update its `@luaname`/`@luadoc`/`@luaexample` tags (and `@luagroup`/`@luaheading` if it's part of a documented pair/group) in the same change** — the published Lua API reference (`popolony2k.github.io/scarab/lua-api/`) is generated straight from these source comments by `scripts/generate_lua_api_docs.py`, not hand-written separately, so this *is* updating the docs, not a separate step from it. `ci.yml`'s `lua-api-docs` job hard-fails on any registered primitive with no `@luaname` tag, so a genuinely missing one fails CI rather than silently shipping undocumented — but a present-but-empty/misleading tag isn't caught mechanically, so still write it like the reference it is.
- **The same applies to every enum constant array exposed to Lua** — any `static const stNamedConstant name[] = { ... }` (registered via `LuaEngineUtil::RegisterConstants`, typically inside a `RegisterEnums()` method; this is a *different* registration mechanism than `lua_register()`, mirroring raylib/`SunLight::Engines`/`SunLight::Input` enums 1:1 as plain Lua globals) needs an `@luaconstants{<display title>}` tag (optionally with `@luadoc`) on the comment immediately preceding the array declaration itself — same generator, same `ci.yml` hard-fail on a missing tag. **This one is easy to genuinely forget**, since a constant array isn't "a new primitive" in the usual sense and was in fact completely unhandled — invisible to the generator entirely — until 2026-09-01, when a user found live that every `KEY_*`/`GAMEPAD_BUTTON_*`/etc. constant Scarab exposes was undocumented anywhere except incidentally, wherever some unrelated primitive's own `@luaexample` happened to mention one by name. Before that fix, `luainputapi.h`'s own class comment even carried a hand-written, self-admittedly-partial `## Constants` list ("full lists in `src/lua/luainputapi.cpp` if you need one not shown here") as a stopgap for exactly this gap — removed once real generation made it redundant. If you add a new `RegisterEnums()`/`stNamedConstant` array anywhere and it isn't showing up on the published site, this is almost certainly why.
- **Every `.cpp`/`.h` file under `src/` starts with the zlib license notice** (`docs/HEADER.txt`, copied verbatim as the file's first lines, one blank line before whatever comes after — a file's own `/** @brief */`-style description comment, if it has one, follows the license notice rather than replacing it) — matching `sunlight`'s own convention. Any new source file must carry it too; this is a copyright/licensing requirement, not a style nicety, so it's not optional the way most of this section is a "match existing style" convention.

## Known gotchas

- **A multi-file AngelCode BMFont (`.fnt` + a separate `.png` atlas) could not be loaded via `set_font` at all — a real, verified engine bug, not a path-authoring mistake. Fixed in [sunlight v0.17.3](https://github.com/popolony2k/sunlight/releases/tag/v0.17.3), re-verified live here.** `set_font`'s top-level `.fnt` *text* read always resolved correctly through the mount-based filesystem when testing against a loose directory (raylib's `LoadFileText` wasn't hooked yet at this point in the story — see the follow-up bug below — but a loose directory's own native `fopen()` finds the real file either way, masking that gap entirely). The failure this first fix addressed was one level deeper: sunlight's `RaylibEngine` constructor registers raylib's `::SetLoadFileDataCallback()`, redirecting every raylib-internal *binary* file read (`LoadFileData()`, which texture/image loads go through) to `SunLight::FileSystem::ReadFile()` — correct, and matches every other resource type. But for a multi-file BMFont, raylib's own `LoadBMFont` (`rtext.c`) builds the atlas image's path *internally* as `TextFormat("%s/%s", GetDirectoryPath(fileName), imageFileName)`, and `GetDirectoryPath` always prepends a leading `"./"` when the input doesn't itself start with `/` — the resulting `"./resources/fonts/whatever.png"` then failed to resolve through `PHYSFS_openRead()` (silently — no trace line at all, unlike raylib's own un-hooked default reader). A leading `/` on the top-level `.fnt` path was tried as a workaround and made things *worse* (broke the `.fnt` text read too) — confirmed live building `samples/text` (see `resources/fonts/README.md` for the full isolation story, including a bare-raylib repro proving the exact same files load fine with no such hook installed). **Fix**: `IFileSystem::ToVirtualPath()` (the same funnel already stripping a Windows drive-letter prefix) now also strips a leading `"./"`, and `RaylibEngine`'s callback routes every path through it before calling `ReadFile()` — landed with 3 new sunlight-side regression tests, and re-verified here (2026-09-01) with a genuine `FONT: [...] Font loaded successfully (121 glyphs)` trace where before there was silence. Single-file fonts (TrueType/OpenType, `.ttf`/`.otf`) were never affected — no internally-constructed secondary path involved for those at all. **Refinement, confirmed independently by Caravellius**: even for a multi-file BMFont, this only ever hit a *relative* `set_font` path — `GetDirectoryPath` only prepends `"./"` when the input doesn't already start with `/`, so a path anchored to the `APP_DIR` Lua global (always absolute/`/`-prefixed) was never affected, on any sunlight version — good practice for `set_font` regardless of this bug's fix.
  **Sibling bug, found later, same root shape — `LoadFileText` itself was never hooked at all, unlike `LoadFileData`. Fixed in [sunlight v0.18.1](https://github.com/popolony2k/sunlight/releases/tag/v0.18.1).** The fix above only ever addressed the atlas `.png`'s *binary* read — the `.fnt` file's own *text* content still went through raylib's default, un-hooked `LoadFileText()`, which does a raw `fopen(fileName, "rt")` when no callback is registered (confirmed directly in raylib's `utils.c`). Fine for a loose directory (the real file's on disk either way, masking the gap completely — this is exactly why the fix above's own testing never caught it), silently broken once the game's content lives *only* inside a mounted `.zip` — found live (2026-09-02) by Caravellius running its own already-existing, unencrypted archive-distribution feature with the loose resources moved out of the way, hitting `WARNING: FILEIO: [...] Failed to open text file` / `Failed to load font texture -> Using default font`. **Fix**: a new `FileSystemLoadFileTextCallback`, a near-exact mirror of the existing `FileSystemLoadFileDataCallback` (same `ToVirtualPath()` routing, `MemAlloc`'d `+1` byte for the null terminator `LoadFileText`'s own contract requires), registered via raylib's `::SetLoadFileTextCallback()` alongside the existing `::SetLoadFileDataCallback()` call in `RaylibEngine`'s constructor — re-verified here (2026-09-02) with a genuine `FONT: [...] Font loaded successfully (121 glyphs)` trace from a `.zip` with **zero** loose fallback copy anywhere on disk. **Gotcha within the gotcha, hit live re-verifying this fix**: `set_font`'s own path must still be `APP_DIR`-anchored (absolute) to actually reach into a mounted `.zip` at all — a bare relative path (eg. `"resources/fonts/whatever.fnt"`, no `APP_DIR ..` prefix) resolves against the CWD-mounted-at-`/` fallback instead, which has nothing to do with either BMFont bug and will simply fail to find the file at all when run from an unrelated directory; this is the exact "refinement" already noted above, not a new caveat, but easy to trip over when writing a quick isolated test rather than reusing an existing sample's own established convention.
- **Every entry script must queue at least one `ScriptProcessor` (`sp_*`) command before it finishes running, even if the game has nothing to sequence** — sunlight's own `ScriptProcessor::Compile()` (called once, right after the whole entry script executes, from `EngineHost::LoadLuaScript`) returns `false` if the command queue is still empty, and a failed compile is a fatal engine-startup error (`Error compiling script commands => ...`). Confirmed live building `samples/hello-world` (see `samples/`): a first version with no `sp_*` call at all failed to start with exactly that error, even though `main.lua` itself ran without error — `LuaEngine::RunFile` succeeding is not enough on its own. The fix for a game with nothing worth sequencing is a single trivial, harmless filler command (e.g. `sp_wait(1)`, a 1-millisecond non-blocking pause) purely to satisfy this requirement — there's no "queue nothing" primitive that skips it.
- **`sprite_configure_texture`/`sprite_set_active_sequence` derive a sprite's displayed *height* from the texture's full native height, not from the computed per-frame tile size** (`LuaSpriteApi::ConfigureTexture`/`SetActiveSequence`, `src/lua/luaspriteapi.cpp`) — `nTextureWidth = nNativeWidth / framesByTexture` divides the *width* by the frame count, but the sprite's height is always set from the texture's raw, undivided native height (`GetOrCacheNativeHeight`). This is exactly correct for a simple horizontal strip where every frame's natural height already equals the desired tile height (every asset actually used in `src/lua/` today, and `resources/sprites/sunny_idle_down.png` — 32px tall native height, 32px tile size, no distortion). It is **not** correct for a genuine 2D icon grid (e.g. sunlight's own `monke_variants.png`, a 4×4 grid of 32×32 icons, 128×128 native size) — configuring that via `sprite_configure_texture` would derive a sprite 32px wide (the correctly-divided tile width) but 128px tall (the full, undivided native height), visibly stretching whatever single tile actually gets cropped and drawn. There's no Lua-exposed way to override the derived height. Confirmed live building `samples/collision` (deliberately avoided by reusing one known-good strip asset for both sprites instead — see that sample's own `docs/README.md`). Not a bug exactly (the API's own doc frames it as "equal-width frames laid out horizontally," which a 2D grid genuinely isn't) — but a real, non-obvious trap for anyone reaching for a spritesheet/icon-grid asset without reading that framing closely first.
- `SunLight::Input::KeyboardKey` vs raylib's own global `KeyboardKey` is a real footgun in engine code (see sunlight's own `CLAUDE.md`) — always fully qualify if you touch input handling.
- **The gamepad D-pad is `GAMEPAD_BUTTON_LEFT_FACE_UP`/`DOWN`/`LEFT`/`RIGHT`, not anything named "dpad"** — raylib's own gamepad button naming (which this engine's `GAMEPAD_BUTTON_*` Lua constants mirror exactly, `LuaInputApi::RegisterEnums`) calls the D-pad `LEFT_FACE`; the face buttons (A/B/X/Y or equivalent) are `RIGHT_FACE`. Easy to reach for `RIGHT_FACE_*` by association ("the buttons you press with your right thumb") and get the D-pad backwards, or vice versa. Found live building `samples/input` (see `docs/lua-api/input.html`) — an early version wired `GAMEPAD_BUTTON_RIGHT_FACE_DOWN` for a reset action and never touched `LEFT_FACE_*` (the D-pad) at all, discovered only once a user actually tested with a real controller.
- `stCoordinate2D`/sprite position is top-left anchored, not center-anchored (confirmed via sunlight's own render clip rect and collision code) — a formula like `pos - height/2` doesn't mean "half a sprite-height above center", it means "half a sprite-height above the sprite's own top edge". Worth checking against before assuming any position math matches visual intuition.
- `SunLight::Concurrent::Timer::Start()` runs it's callback on it's own background thread; `lua_State` isn't thread-safe, so any code calling into Lua from both the main thread and a timer callback needs to serialize via a mutex (see `LuaEngineUtil::s_LuaMutex` — lives there, not on `LuaEngine`, since `LuaTimerApi::SetTimer`'s background-thread callback needs it too). Watch for deadlock if a mutex-holding call can trigger `Timer::Stop()` (which `std::thread::join()`s) — the timer thread must not block on the same mutex, or a `join()` from the mutex-holding thread deadlocks against it (fixed via `try_lock` in the timer callback rather than a blocking lock).
- **`s_LuaMutex` only protects the shared `lua_State*` itself — it does NOT protect `EngineHost`/`SoundManager`/raylib's own audio/engine state, which the main thread also touches every frame outside that lock.** A `set_timer` callback (background thread) that calls any Lua primitive reaching into that state — `play_song`/`sound_is_playing` (→ `SoundManager`/raylib directly), any direct-dispatch sound/song call (→ `EngineHost::OnCommand`, touching `m_CurrentSong` etc.) — races the main thread's own identical access with zero synchronization; this can corrupt state or hang the whole game if it lands inside a raylib/miniaudio-internal lock. **Rule for any `set_timer` callback**: it may only ever touch plain Lua data (safe under `s_LuaMutex`, which is all that mutex actually guarantees) — never call a primitive that reaches `EngineHost`, `SoundManager`, `SpritePool`, or any other engine-owned C++ object from inside one; flip a plain boolean flag instead and let a separate per-frame update function read/act on it the next real frame.
- **On Windows, a relative `.json` project file in a subdirectory (`scarab.exe scripts\\foo\\project.json`) failed with `cannot open scripts/foo\\main.lua` — `EngineHost::ResolveEntryScript`'s `.json` branch joined `main_script` onto the project file's directory with `std::filesystem::path`'s `operator/` and took `.string()`, which uses a backslash on Windows, but that path is read through `SunLight::FileSystem` (PhysFS), whose virtual paths only treat `/` as a separator.** A pre-existing bug, invisible until something launched a project from a subdirectory on Windows: a bare `project.json` in the CWD (the documented normal invocation) has an empty `parent_path()`, so no separator was ever inserted. Found live (2026-09-21) by `ci.yml`'s new headless smoke step (Linux/macOS/Windows), which passed on 3 of 4 platforms and failed only here. Fixed with `.generic_string()` (forward slashes; identical to `.string()` on Linux/macOS). Any new code that builds a path with `std::filesystem` and then hands it to `SunLight::FileSystem` needs the same `generic_string()`.
- **A map with EXTERNAL tilesets (`.tsx`) or object templates (`.tx`) could not be loaded from a `.zip` or an encrypted pack — a real, verified engine bug: libtmx opened them straight from the OS path, never through `SunLight::FileSystem`. Fixed in [sunlight v0.31.0](https://github.com/popolony2k/sunlight/releases/tag/v0.31.0), re-verified here (Scarab v0.1.20).** `tilemap_load_map` failed with `Cannot load map: xml parser: cannot open extern tileset '<path>/x.tsx'` for any packed game whose maps reference a `.tsx`. The `.tmx` itself was always read fine through the mount-based filesystem (sunlight reads it into a buffer and hands libtmx `tmx_rcmgr_load_buffer_vpath`), which is exactly why nothing looked wrong until the failure was one level deeper: the map's own external references. Hidden in every normal build for the same reason as the two BMFont bugs above — loose resources sit next to the executable (or in the CWD), so libtmx's raw `fopen()` found the real file anyway; it only broke once someone shipped *only* the `.zip`/encrypted pack. An **encrypted** pack was doubly affected: even where a path resolved, libtmx's raw read could never apply the decrypting read filter. Found live (2026-09-21) when sunlight flagged that libtmx bypasses the FileSystem and Scarab's own shared `resources/tilemap/test.tmx` (8 external `.tsx`) plus Caravellius' `corsair.tmx` (1) both use external tilesets; Caravellius then reproduced it on its real `caravellius.zip` (the demo session fails at ~230 virtual seconds when it loads `corsair.tmx`). **Fix**: `LoadMap` reads the external references up front through the FileSystem and gives libtmx the buffers via its Resource Manager (keyed by the raw `source`/`template` attribute text; each reference resolved against the directory of the file that names it, `..`/backslashes normalised, a template's own tileset loaded first, tileset images resolved against the tileset's directory); anything the FileSystem can't provide falls back to libtmx's own lookup, so loose folders behave as before. **Regression test**: `scripts/tileset_archive_smoke.py` (pure Python — `zip` doesn't exist on Windows) builds a project from this repo's own `resources/tilemap`, runs it headless from an EMPTY directory as a plain `.zip` and (`--require-encrypted`, which `ci.yml` passes on all 4 platforms) as an encrypted `scarab --pack` archive; the project's script quits itself only if the map loaded at 20x20, so a failure is exit 3 with the scarab log attached. It was shown failing first against sunlight v0.29.0 (the exact error above), passes on v0.31.0, and the encrypted archive was confirmed to really be ciphertext (no `<tileset` in the packed `.tsx`'s bytes) so the test genuinely exercises the read filter. Also re-verified with Caravellius' real acceptance entry run from its `caravellius.zip` in an empty directory (`PASS`, intro sync exactly 84.000s). Any new packed-content feature deserves the same "run it from ONLY the archive, in an empty directory" test — a loose copy nearby is what hid this.
- **The renderer does not exist when the Lua engine is built or when the entry script starts — the entry script now runs BEFORE the window, and every renderer-needing primitive reaches the renderer through `LuaEngineUtil::GetTileMap(L)`/`GetDrawSurface(L)`, which create the default renderer on first use (Scarab v0.1.21 groundwork; behaviour-preserving).** Before, `main()` created and `Start()`ed a renderer, built `EngineHost` with raw `ITileMap*`/`IDrawSurface*` (stashed as Lua light-userdata globals `tileMapPtr`/`drawSurfacePtr`), and the entry script ran on the first frame inside the loop. Now those globals are gone: one `rendererProviderPtr` (an `Engine::IRendererProvider`) is stashed instead, `GetTileMap`/`GetDrawSurface` ask it (creating the default renderer + opening its window if none exists, and recording the calling primitive's name via `lua_getinfo("n")` so a later `renderer_create` can say who created it implicitly), the collision listener attaches through the provider's created-hook (`LuaEngine::AttachToTileMap`), and `EngineHost::InitEngineStateHandler` just keeps the old one-frame gap (frame numbering, and every virtual-clock timestamp derived from it, is unchanged — verified: Caravellius' ACCEPT output is byte-identical before and after). **Traps for new code**: (1) a primitive that needs a live window/GL context but never calls `GetTileMap`/`GetDrawSurface` (today only `sprite_configure_texture`, which loads a GPU texture) must call `LuaEngineUtil::EnsureRenderer(L)` first, or it would touch a renderer that doesn't exist yet; (2) something that must be readable before any window (the headless `os.time`/`os.clock` overrides) must use `IRendererProvider::PeekDrawSurface()` — which never creates one — not `GetDrawSurface`; (3) renderer-free primitives (`load_json`, `dofile`, `sound_*`, `sp_*`, `pool_*`, sprite handle ops, `set_timer`, `crypto_*`, `pack_*`) must stay that way — don't add a `GetTileMap` call to one, or a script calling it before its own window setup silently creates the default renderer. Verified on the real thing, not assumed: headless smoke + tileset-archive tests (plain and encrypted) pass, the 54-row alignment/scroll probe is identical, all 13 samples run headless and 7 in a real window, a script that fails at load exits `[FATAL]`/1 in 0.06s with no window loop, and one that never uses a window primitive still gets its renderer when it finishes.

- **`--headless` (null renderer) has a virtual clock, and a few things deliberately stay on real time or need care.** Each frame advances sunlight's `VirtualClock` by exactly `1 / target FPS`; `app_get_time()`, `sp_wait`, sprite frame animation, tile animation and `EngineHost`'s 2000ms sprite-queue check (via `SunLight::General::Clock`) all follow it, and Scarab replaces Lua's `os.time`/`os.clock` to follow it too (`os.time()` = the real epoch second at install + whole virtual seconds, rounded to the nearest millisecond first — found live: 300 frames at 60fps accumulates to `4.999999999999988`, which a plain truncation floors to 4). **`set_timer` stays real-time** (its `Timer` is a real `sleep_for` thread), and — extending the timer-callback rule above — **calling `os.time()`/`os.clock()` inside a `set_timer` callback is unsafe in headless mode**, since the replacements read engine state (`IDrawSurface::GetElapsedTime`), which `s_LuaMutex` doesn't protect. Other null-backend facts worth knowing: the backend is process-global (one backend per run — `Create` refuses to mix a null and a real renderer); anything created through the engine (eg. textures via `sprite_configure_texture`) must be released before the null renderer is destroyed, same as the real backend; and `GetElapsedTime` is 0.0 before `Start()` and restarts at 0 on every `Start()`. **Found live during the first null-backend acceptance run (2026-09-20), fixed in sunlight v0.26.1 and re-verified here**: the virtual clock originally *accumulated* `t += 1/fps` per frame, so `GetElapsedTime()` undershot exact boundaries (5040 frames read `83.99999999999652`, not 84.0) and any game waiting for `elapsed >= start + D` at a whole-second `D` lost one extra frame per wait — Caravellius' intro sync came out 84.133s instead of 84.0 (8 waits = 8 extra frames). sunlight v0.26.1 counts frames instead of summing them (`base + framesSinceBase / fps`, one division — `300/60 == 5.0` and `5040/60 == 84.0` bit for bit), and Caravellius' intro sync now reads exactly 84.000s. Lesson: when a virtual clock is involved, assert `GetElapsedTime()` *exactly* at frame counts that should land on whole seconds, not within a tolerance (sunlight's own tests used a 1e-9 tolerance, which is why they missed it).
- **`dt`, as passed to every Lua `on_update` callback, is NOT a real measured frame time — it's a fixed `#define __FRAME_DELTA_MILLI (1000 / 60)` (`enginehost.cpp`), and that's *integer* division, truncating to `16`, not even the true `16.666...`.** Any Lua-side counter that accumulates `dt` to track real elapsed time (a timeout, a cooldown meant to correspond to real seconds) silently drifts slow against real wall-clock time by design — roughly 40ms slow per real second (~4%) from the truncation alone, compounding forever with no self-correction, and gets *worse* under real frame-rate variance (a slow frame that actually took 50ms of wall-clock time is still reported as exactly 16ms of `dt`, that difference is simply invisible to Lua). For anything tracking real elapsed time over a long, continuous duration, compare Lua's own `os.time()` (real wall-clock seconds since epoch, part of Lua's standard library) against a start timestamp directly, every frame, instead of accumulating `dt` — no accumulation error at all, since each check is against absolute real time rather than a running sum of approximations. `dt` itself remains fine for short, gameplay-feel timings (a few percent of drift over a couple of seconds is imperceptible); `os.time()` is specifically the better tool for anything longer. **Where whole-second granularity is too coarse** (a per-character typewriter reveal, a cutscene timeline that has to line up with a song), use `app_get_time()` instead — the same "anchor to a start timestamp, compare each frame" pattern, but real sub-second wall-clock time (monotonic, raylib's `GetTime()`, since window init). Found live (2026-09-19) by Caravellius: its intro storyboard's `dt`-accumulated typewriter reveal visibly outlasted its own BGM on a ~45 FPS machine.
- `sprite_set_active_sequence(handle, sequenceId)` unconditionally resets the target sequence's own animation state, even when it's already the active sequence — confirmed via sunlight's own source (`Sprite::SetActiveTextureSequence`, `build/_deps/sunlight-src/src/sprite/sprite.cpp`) unconditionally calling `Reset()` on the newly-selected sequence's `TextureCanvas`. Calling this every frame regardless of whether the sequence actually changed silently freezes any `AUTOMATIC_CIRCULAR`/`AUTOMATIC_RIGHT_LEFT` animation on that sequence at it's first frame forever, since the reset undoes each frame's own advance before it's ever drawn. Always track the last sequence actually set (per-sprite) and only call this again when it genuinely changes. Full primitive doc + a worked pose-following pattern are at [popolony2k.github.io/scarab/lua-api/sprite.html](https://popolony2k.github.io/scarab/lua-api/sprite.html) (or `LuaSpriteApi::SetActiveSequence`'s own doc comment in `src/lua/luaspriteapi.cpp`, which that page is generated from).
- Acquiring/positioning/`sprite_add_to_layer`-ing a sprite from a Lua module's own top-level (load-time) code fails silently and leaves it invisible, if that code runs before the map is actually loaded — a game's own entry script's `dofile`/init-style calls all happen synchronously *before* a queued `sp_load_stage` command (if any) has been dispatched, so any sprite setup at that point runs before `LoadMap` does (that only happens on the first `STATE_STAGE_RUNNING` tick that actually processes the queued stage-load). A consuming game's own modules should defer real sprite acquisition to a later, genuinely per-frame or wave-spawn-triggered hook, not top-level load-time code.
- `CMAKE_CXX_STANDARD 17` must be set **unconditionally** in the root `CMakeLists.txt`, not gated behind `if(APPLE)` — it originally was (added only for some Apple-specific raylib defines, long before this repo used `std::filesystem`). That meant Linux/GCC and Windows/MSVC builds never got an explicit standard flag and silently fell back to each compiler's own default, which can be pre-C++17 — breaking `std::filesystem` (`enginehost.cpp`'s `ResolveEntryScript`) with a confusing compile error instead of a clear "wrong standard" message. Found by actually building on Linux, not by code review — a macOS-only compile gives zero signal here. `CMAKE_CXX_STANDARD_REQUIRED ON` is set alongside it so an incompatible compiler hard-errors instead of silently downgrading again in the future.
- `EngineHost::OnStop()` must release `SpritePool`'s textures (`m_SpritePool.Clear()`) — it can't be a no-op. `TileMapRenderer::Stop()` (sunlight) calls every listener's `OnStop()` *before* `CloseWindow()` tears down the GL context, specifically so listeners get a chance to free GPU resources while the context is still valid; if `SpritePool`'s textures are instead released later, by `~SpritePool()` at program exit, that happens *after* the context is already gone — `TextureCanvas`'s destructor calling into raylib to unload a texture at that point segfaults (`rlUnloadTexture`). Symptom looks exactly like a random exit-time crash (e.g. via ESC) with no obvious connection to whatever was touched most recently — check `OnStop()`/shutdown ordering before assuming an exit crash is caused by recent unrelated changes.
- `sprite_set_pos(handle, x, y)`'s C++ binding (`LuaSpriteApi::SetPos`) reads `x`/`y` via `lua_tointeger`, which **silently fails on a genuinely fractional float** (writes 0, doesn't truncate) rather than rounding/truncating it. Any Lua-side position math should always be truncated (e.g. `math.floor`) before calling `sprite_set_pos`, even values that "shouldn't" end up fractional (e.g. an integer base plus a non-integer per-frame velocity) — skipping this doesn't error or warn, it just makes the sprite appear to silently stop moving partway (every other frame's write fails, leaving the position wherever the last successful *integer* write left it), a confusing, hard-to-diagnose symptom with no exception or log line pointing at the cause.
- **A layer's own `visible` flag in a `.tmx` gates every runtime sprite registered against that layer id too, not just it's static tile/object content — parent-child visibility, by design.** sunlight's `TileMapRenderer::DrawAllLayers` is the only path to `HandleSpriteUpdate` (the call that draws a sprite via that dispatch route), gated on `pLayer->visible` for every layer type — a sprite's own `sprite_set_visible` only ever gets a say once it's container layer is itself visible. Any map-authoring convention that uses genuinely empty placeholder object-group layers as sprite anchors must author them visible (`visible="1"`, or the attribute omitted — Tiled defaults to visible when absent), not `visible="0"`, or every sprite registered against that layer id silently never draws at all. To hide a whole layer's sprites at runtime as a group, use `tilemap_set_layer(layerId, false, ...)` (already exposed to Lua) rather than authoring the layer invisible from the start.
- **Not every C++ entry point that loads Lua actually goes through `SunLight::FileSystem` just because most do** — `LuaEngine::RunFile` (loads a game's very first script, called once from `EngineHost::LoadLuaScript`) used to use the raw C API's `luaL_dofile`, which reads via it's own internal `fopen()`, completely bypassing the mount-based filesystem layer every *other* Lua/JSON/texture/sound/tilemap load already routes through (`LuaFileSystemApi::DoFile`'s overridden `dofile` global, `LuaJsonApi::LoadJson`, `RaylibEngine`'s texture callback, `RayLibSound::Load`, `TileMapRenderer::LoadMap`). This is exactly the one call that has to succeed before an archived (`.zip`) game can even start — every other subsystem can work while the very first script inside a mounted `.zip` still can't be reached at all. Fixed to read via `IFileSystem::ReadFile` + `luaL_loadbuffer`/`lua_pcall`, mirroring `LuaFileSystemApi::DoFile`'s own pattern. If a future change adds another direct-to-`lua_State` script-loading entry point (bypassing the already-overridden `dofile` global), it needs this same treatment explicitly — routing through `SunLight::FileSystem` is not automatic just because it's the norm elsewhere in this codebase.
- **`main.cpp` mounts two separate things for two separate reasons, and both are load-bearing** — `APP_DIR` (the executable's own directory) mounted at itself, and the process's current working directory mounted at the virtual root ("/"). These aren't redundant: `EngineHost::ResolveEntryScript`'s `.json` branch deliberately resolves `main_script` *relative to the project file itself*, not `APP_DIR` (so a project stays relocatable as a whole) — for the documented normal invocation (`./scarab project.json`, a bare relative path), that produces a bare CWD-relative resolved path, which only the CWD-at-root mount can answer; the `APP_DIR`-at-itself mount only answers absolute, `APP_DIR`-prefixed virtual paths (what `.zip` entries and every `APP_DIR`-anchored Lua/JSON load actually use). Removing either mount reintroduces a real regression — a plain relative-path project launch fails with "cannot open" the moment `LuaEngine::RunFile` routes through `SunLight::FileSystem` (see the gotcha above) without the CWD mount also in place. Don't assume one of these two `Mount()` calls in `main.cpp` is dead code without re-deriving why both exist.
- **A released macOS binary that works fine on the machine that built it can still be completely broken for anyone else — "builds and runs here" is not the same as "relocatable."** Found live (2026-08-29) while dry-running a `FetchContent`-based *binary* consumption mode for a downstream project (see `caravellius`/`game-engine`'s own split-plan notes): the real `v0.1.0`/`v0.1.1` released macOS archives failed immediately once extracted anywhere outside the CI runner that built them — `dyld: Library not loaded: @rpath/libsunlight.dylib`. `otool -l` confirmed why: `scarab`'s (and `libsunlight.dylib`'s and `libtmx.*.dylib`'s) `LC_RPATH` entries were the *CI runner's own absolute build-tree paths* (`/Users/runner/work/scarab/scarab/build/_deps/...`) — CMake's default rpath is correct for running straight out of the build tree, but nothing converts that into something portable before packaging, since Scarab has no `install()` step (the build output *is* what `release.yml` ships verbatim). Fixed via `set_target_properties(scarab sunlight tmx PROPERTIES BUILD_WITH_INSTALL_RPATH TRUE INSTALL_RPATH "@loader_path")` on macOS (`"$ORIGIN"` on Linux) — `raylib`/`LibXml2` needed no fix, neither had an `LC_RPATH` entry pointing at another FetchContent'd target's build dir. **This fix alone then exposed a second, previously-masked bug**: `raylib`/`tmx`/`LibXml2` (unlike `sunlight`, which sets no `VERSION`/`SOVERSION`) each build as a real versioned file *plus* a SOVERSION symlink matching the dylib's own embedded install name (e.g. `libraylib.5.5.0.dylib` real file, `libraylib.550.dylib` symlink — what every other binary's `@rpath` reference actually looks for) — `scarab_copy_binaries` only ever copied `$<TARGET_FILE:X>` (the real, fully-versioned file), never the symlink, so the old build-tree-absolute rpath happened to paper over this by searching the *original* build directory (where the symlink still existed) instead of the flattened copy directory. Fixed by also copying `$<TARGET_SONAME_FILE:X>` for `raylib`/`tmx`/`LibXml2` (a no-op duplicate for `sunlight`, which has no separate SONAME file). **Verified via a real relocation test** — copy the flattened build output to a directory with zero connection to the original build tree, run `scarab --help` from there — both before (failed, confirming the bug) and after (succeeded) each fix. `release.yml` now runs this exact same relocation test itself (`Smoke test (Linux/macOS)`/`Smoke test (Windows)` steps, right after staging and before packaging) specifically so a regression here — or an equivalent problem on Linux/Windows that couldn't be verified locally on this one macOS dev machine — fails the release loudly instead of shipping silently broken again. **This exact class of bug is CONFIRMED (not just suspected) in `sunlight`'s own released artifacts too** (a separate repo, fix prototyped/verified in the cached `build/_deps/sunlight-src` checkout per the usual cross-repo hand-off process, not committed from here) — its `release.yml` does run a real `cmake --install` (unlike Scarab), but CMake's default `INSTALL_RPATH` target property is empty unless a project explicitly sets one, so `install()` alone doesn't automatically make a shared library's rpath portable either. Verified directly: a real `cmake --install` of sunlight's own source produced an installed `libsunlight.dylib` with **zero** `LC_RPATH` entries, and actually `dlopen()`-ing it failed immediately (`Reason: no LC_RPATH's found`) — worse than Scarab's original bug, since there was no working case at all, not even on the machine that built it. Fixed there with `set_target_properties(sunlight tmx PROPERTIES INSTALL_RPATH "@loader_path;$ORIGIN")` right before its own `install(TARGETS sunlight raylib tmx ...)` call (no `BUILD_WITH_INSTALL_RPATH` needed there, unlike Scarab — sunlight has a real `install()` step for `INSTALL_RPATH` to apply to normally) — re-verified with a real install + relocation test, load succeeded both right after install and after copying the installed files to an unrelated directory.

**A second real regression, found via the actual CI run (not caught locally, since this machine is macOS-only)**: `$<TARGET_SONAME_FILE:X>` is a **hard CMake configure-time error on Windows** — `TARGET_SONAME_FILE is not allowed for DLL target platforms` — since Windows DLLs have no SONAME/versioned-symlink concept at all. The first version of this fix broke Windows configure entirely (confirmed via a real `v0.1.2` CI run: Linux and both macOS architectures' `Smoke test` steps all passed cleanly, proving the rpath+SONAME fix genuinely works across every Unix platform tested, not just this one dev machine — but Windows failed at `Configure`, before `Build` even ran). Fixed by moving the `$<TARGET_SONAME_FILE:X>` copies out of `scarab_copy_binaries`'s main `COMMAND` list into a separate `add_custom_command(TARGET scarab_copy_binaries POST_BUILD ...)` block guarded by `if(NOT WIN32)`, mirroring this file's own existing pattern for the Windows-only Iconv/zlib DLL copies. **Lesson generalizable beyond this one bug**: a fix verified only on the one platform available locally can still break a platform that was never tested — the real CI matrix is what actually caught this, not local verification alone.

- **A published release archive can be missing an entire directory the local build genuinely has, with nothing in `release.yml` ever erroring — `release.yml`'s own "Stage artifact" steps pick specific files by name/glob, they don't just copy everything `scarab_copy_binaries` produced.** Found live shipping `v0.1.11` (the per-release shared `SCARAB_CONTENT_KEY` feature, whose entire stated purpose was letting someone try `--pack` from a downloaded binary alone) by Caravellius actually testing that binary-mode workflow end-to-end against the real published archive, not this repo's own local build — `scarab --pack <config.json>` failed with `Lua error: cannot open .../tools/pack.lua`. Root cause: `scarab_copy_binaries` (`CMakeLists.txt`) has always copied `tools/` next to the built executable locally, but the three `Stage artifact` steps in `release.yml` only ever named the executable and shared-lib glob patterns (`*.so*`/`*.dylib`/`*.dll`) — `tools/` was never in that list, so every real release archive (not just `v0.1.11`) has always shipped without it, completely invisibly, since nothing about that omission fails a copy command or an existing `--help`-only smoke test. **Fixed** by adding an explicit, unconditional `tools/` copy to all 3 `Stage artifact` steps (`cp -r`/`Copy-Item -Recurse` — no `|| true`/`-ErrorAction SilentlyContinue` swallowing a real failure, unlike the shared-lib copies, since `tools/` always exists). **Also strengthened the smoke test itself**, since the existing `--help`-only check is exactly why this shipped unnoticed in the first place — `--help` never touches `tools/pack.lua` at all. Both `Smoke test` steps now also pack a tiny synthetic source directory via `--pack` against the relocated archive and confirm a real output `.zip` gets written, so this exact class of bug — this file missing, or any future regression in the packaged archive's own completeness — fails the release loudly instead of shipping silently broken again, the same philosophy as the rpath/SONAME smoke test just above. Verified locally before pushing: simulated the fixed staging + smoke test end-to-end with a real key configured (matching what `release.yml`'s own `Configure` step actually does) — `--pack` genuinely succeeds and produces a valid encrypted archive from the relocated, `tools/`-inclusive copy.
