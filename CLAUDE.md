# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

## Project overview

This repo is a monorepo distributing the **sunlight** 2D game engine and the games built on it. Only game today: **Caravellius** (`games/caravellius`), a vertical-scrolling space shooter (Galaga/1943-like) in C++17 using raylib for rendering/input/audio and Tiled (`.tmx`) maps for stages.

The engine layer built on top of `sunlight` (see the Architecture section below) is itself called **Scarab** — hence its C++ namespace, `Scarab::*` (`Scarab::Host::EngineHost`, `Scarab::Lua::LuaEngine`, `Scarab::Engine::*`), and hence the built executable itself is named `scarab`, not `caravellius` (see Build section). **Caravellius** is the game; it consists entirely of `games/caravellius/` (`resources/` - Lua scripts, JSON configs, sprites/audio/tilemaps - plus `project.json` and a small `CMakeLists.txt` that only bundles those assets next to the already-built `scarab` executable). Scarab's own C++ (`src/` at the repo root) and its build (the root `CMakeLists.txt` - `FetchContent`, `add_executable(scarab ...)`, everything) live outside `games/caravellius/` *specifically* so that folder is the one piece expected to move out when Scarab and Caravellius eventually split into separate projects (the stated long-term plan) - `src/` used to sit under `games/caravellius/src/` before that move, which is why older history/memory may still say that.

`sunlight` itself is **not** in this repo — it's fetched via CMake `FetchContent` from `github.com/popolony2k/sunlight`, pinned to a tagged release (`GIT_TAG v0.14.0`; previously `v0.13.2`, `v0.13.1`, `v0.13.0`, `v0.12.0`, `v0.11.0`, `v0.10.0`, `v0.9.1`, `v0.9.0`, `v0.8.0`, `v0.7.0`, `v0.6.0`, `v0.5.0`, `v0.4.0`, `v0.3.0`, `v0.2.2`, `v0.2.1`, `v0.2.0`, and `v0.1.0` before that — bump the tag deliberately when sunlight cuts a new release, rather than floating on `main`). If you need to read or modify engine internals rather than game code, that's a separate repo; a cached checkout may exist locally under `build/_deps/sunlight-src` after a configure, and it ships its own `CLAUDE.md`.

**`SCARAB_TODO.md`** (repo root) tracks engine-level work items for Scarab (and possibly sunlight) earmarked to start once Scarab and Caravellius actually split into separate repos (see the "Scarab/Caravellius split" note below) — Scarab gets it's own independent phase planning at that point, and this file is the seed of it. Not to be acted on before the split happens.

## Build

```shell
cmake -B build -S .
cmake --build build -j 4
```

On Windows, `libxml2`/`tmx` (both fetched transitively via sunlight) link vcpkg's `iconv`/`zlib` dynamically, so `CMAKE_TOOLCHAIN_FILE` must point at vcpkg's toolchain — this is expressed as a real CMake config, not an IDE setting: `CMakePresets.json`'s `windows-vcpkg` preset (`condition`-gated on `hostSystemName == Windows`, so it's inert/invisible everywhere else) sets it from the `VCPKG_ROOT` environment variable. Configure with `cmake --preset windows-vcpkg` instead of the plain invocation above (works identically from a bare terminal, Visual Studio, CLion, or VSCode — `.vscode/settings.windows.json`'s `cmake.configurePreset` just points VSCode's CMake Tools at the same preset name, it doesn't duplicate the toolchain path). A per-OS `.vscode/settings.<os>.json` split exists (swapped into `settings.json` by the recommended `franmastromarino.vs-code-settings-os` extension) purely as VSCode-integration convenience — it must never carry `cmake.configureSettings`/cache-variable values of its own, since that was the actual bug once (a Windows session's own hand-added `CMAKE_TOOLCHAIN_FILE` in the *shared, git-tracked* `.vscode/settings.json` broke Mac/Linux configure outright, since VSCode settings have no OS conditioning — `${env:VCPKG_ROOT}` resolved to a literal, nonexistent path there). CMake itself must remain the single source of truth for anything platform-conditional.

`CMakePresets.json` also has a `default` preset (no toolchain overrides, `condition`-gated to `hostSystemName != Windows`), which exists purely to give VSCode's CMake Tools extension something to select on Mac/Linux — once *any* `CMakePresets.json` is present in a workspace, that extension switches into "a preset must be chosen" mode for its own configure UI, even though a plain CLI `cmake -B build -S .` never looks at presets at all unless you pass `--preset`. Before this preset existed, deleting `build/` and reconfiguring through VSCode on Linux/Mac hit an empty picker with no valid option but "Add new preset..." (`windows-vcpkg`'s condition filtered it out, and nothing else was defined). `.vscode/settings.linux.json`/`settings.macos.json` set `cmake.configurePreset: "default"` so the picker doesn't prompt at all in the normal case.

Debug symbols: `cmake -B build -S . -DCMAKE_C_FLAGS="-g2" -DCMAKE_CXX_FLAGS="-g2"`.

Lua backend defaults to `walterschell/Lua` (CMake-friendly). `-DSCARAB_USE_OFFICIAL_LUA_FTP=ON` switches to the official Lua 5.4.6 FTP tarball build (Unix-only).

The root `CMakeLists.txt` globs sources with `GLOB_RECURSE "src/*.cpp"` — re-run `cmake -B build -S .` after adding new `.cpp` files so the glob picks them up. (The pattern must be one combined `"src/*.cpp"` expression, not two separate arguments `"src" *.cpp` - the latter globs unscoped from `CMAKE_CURRENT_SOURCE_DIR`, which silently swept up `FetchContent`'d dependencies' own `.cpp` files from `build/_deps/` once this ran from the repo root; a real, if previously-harmless, bug exposed by moving `src/` here.)

The built executable now **requires** a command-line argument — either a `.lua` entry script path or a `.json` project file (see `project.json`/`main_script` below) — and refuses to start at all without one. Run it as `./scarab project.json` (or `./scarab resources/scripts/main.lua` directly) from the build output directory. The executable is named `scarab`, not `caravellius` — it's built entirely from Scarab's own C++ (confirmed zero `Caravellius::*` namespace remains anywhere in the source), and which game it actually runs is determined at launch by the entry-point argument, not compiled in; naming the binary after one specific game would bake in an assumption the whole entry-point design exists to avoid.

`scarab_copy_binaries` (root `CMakeLists.txt` - Scarab's own runtime deps: raylib/tmx/libxml2/sunlight) and `caravellius_copy_resources` (`games/caravellius/CMakeLists.txt` - `resources/{configs,scripts,tilemap,sprites,audio}` and `project.json`, `add_dependencies`'d onto `scarab_copy_binaries` and onto `scarab` itself, since `add_custom_command(TARGET ... POST_BUILD)` can only attach to a target defined in the *same* directory as the attaching call - `scarab_copy_binaries` lives one directory up from `games/caravellius/CMakeLists.txt`, so that file uses a separate target + `add_dependencies` instead) both copy into the build dir next to the executable. This used to silently copy into the wrong location: its destination paths used `${CMAKE_CURRENT_BINARY_DIR}/$<CONFIG>/`, but this project's `CMAKE_BUILD_TYPE` is cached as `Debug` (making `$<CONFIG>` evaluate to `"Debug"`) while the actual `scarab` executable lands directly in `${CMAKE_CURRENT_BINARY_DIR}` with no per-config subdirectory (Unix Makefiles is single-config and doesn't use one) — so every resource ended up copied into an unused `build/Debug/` next to the real, un-updated copy the running executable actually reads (`build/games/caravellius/Debug/`, back when this logic lived in `games/caravellius/CMakeLists.txt`), while the build log still printed "Copying..." and "Built target" either way. Fixed by using `$<TARGET_FILE_DIR:scarab>` instead, which always resolves to wherever the executable's own output actually lands, regardless of generator/config setup — confirmed by direct testing that a plain `cmake --build` (no reconfigure) now reliably propagates a resources-only edit. If a stray `Debug/` directory reappears next to `build/scarab`, that's this same class of bug back again — `diff` the source and build-dir copies before assuming a Lua-only change is broken; a live bug and a stale copy look identical from the running game's behavior alone.

No test suite exists for Caravellius. There is no linter/formatter config; match the existing style (see below).

## Architecture (games/caravellius)

C++ is a thin, game-agnostic engine layer; all game logic (every enemy type, the player ship, config/stage bootstrap) lives in Lua. This is the end state of a completed 9-phase refactor (see "Lua migration" below) — there is no legacy per-sprite C++ state-machine path anymore.

- `src/main.cpp` — entry point. Requires `argv[1]` (a `.lua` script or `.json` project file) — prints a usage message and exits before constructing anything if it's missing, so a forgotten argument never even opens a window. Builds a `SunLight::Renderer::TileMapRenderer` (window/game loop owner) and a `Scarab::Host::EngineHost` (passing `argv[1]` straight through), wires the latter as a tile-map listener, then `Start()`/`Run()`/`Stop()`.
- `games/caravellius/project.json` — the project's own entry-point descriptor, `{"main_script": "resources/scripts/main.lua"}`, copied next to the executable at build time. Not the only way in — `EngineHost::ResolveEntryScript` accepts either this (a `.json` file, read via `nlohmann::json` before any Lua exists, `main_script` resolved relative to *the project file's own directory*, not `APP_DIR`) or a bare `.lua` path passed directly as `argv[1]`, told apart by extension. There is no compiled-in default (the old `__MAIN_LUA_ENTRY_POINT_FILE` `#define` is gone) — every launch must name one explicitly, and a bad/missing one is a normal fatal-error case (`EngineHost::OnError`/`FatalErrorHandler`), not a silent fallback.
- `src/host/enginehost.{h,cpp}` — `EngineHost`: sound playback, the `ScriptProcessor`/`LuaEngine` wiring, the engine's own state machine (init/run-stage/fatal-error handlers), and `OnCommand` dispatch. Owns no game logic at all — `InitEngineStateHandler` just runs `main.lua` and transitions to `STATE_STAGE_RUNNING`; `OnCommand`'s `LOAD_STAGE_CMD`/`MOVE_SPRITES_TO_SCREEN_CMD` cases both give Lua first (and only) refusal via `LuaEngine::TryDispatchLoadStage`/`TryDispatchMoveSpritesToScreen`, reporting an error if Lua doesn't claim a valid id (there's no C++ fallback left to drop to). `CheckSpritesQueueEmpty` is the one piece of per-frame bookkeeping that isn't state-machine or Lua-dispatch — a periodic (2000ms) check that resolves `sp_wait_queue_empty()` via `LuaEngine::GetActiveEnemyCount()`. Not a collision listener — `Scarab::Engine::Lua::LuaCollisionListener` (registered by `LuaEngine::Init`) is the sole collision authority now that every sprite is Lua/`SpritePool`-owned. (This used to be split across a `WorldBase` base class + `EngineHost` subclass; merged since nothing else ever subclassed `WorldBase`.) No longer sets up any collision rule itself, either — the 3 `AddColliderToColliderRule` calls (player-vs-enemies, player-vs-enemy-bullets, player-bullets-vs-enemies) that used to live in `EngineHost`'s constructor, keyed off a private `__SpriteLayerId` enum, moved to `Bootstrap.setup_collision_rules()` (`resources/scripts/bootstrap.lua`) via the already-existing `collision_add_rule` Lua primitive — which layers collide with which is Caravellius game design, not engine plumbing. Sprite layers map to fixed Tiled layer IDs (`LAYER_PLAYER_SHIP=1`, `LAYER_ENEMIES_SHIPS=2`, `LAYER_PLAYER_SHIP_BULLETS=3`, `LAYER_ENEMY_BULLETS=4`, now defined in `resources/scripts/layerids.lua`) — these **must** exist in any Tiled map used. This isn't just a Lua-side convention: `sprite_add_to_layer` resolves the layer id via sunlight's `tmx_find_layer_by_id` against the actually-loaded `.tmx`, and silently no-ops (`AddSprite` returns `false`, nothing renders, no error anywhere) if that id isn't a real layer in the map. **Full map-authoring requirements for the art team (required layers, the empty-objectgroup pattern used for 2-4, boss/sub-boss trigger-mark conventions including the "fires at the TOP of the viewport, not the bottom" gotcha) are written up in `games/caravellius/docs/MAP_AUTHORING.md`** — read that before creating or editing any stage `.tmx`, don't rely on this paragraph alone. No longer auto-scrolls the camera either, or holds an `ITileMap*` of its own at all — `ScrollDown()`'s fixed-cadence (`__MAX_FPS_PER_SCROLL`) `MoveCameraDown()` call moved to `resources/scripts/camera.lua`'s `Camera.update` (registered via `Enemies.register_update`, same per-frame dispatch every enemy/player module uses), using the already-existing `camera_move_down()` Lua primitive; the constructor's `pTileMap` parameter is now forwarded straight into `LuaEngine::Init` without ever being stored as a member, since that was its only remaining C++-side use. `OnStop()` is no longer a no-op — it calls `m_SpritePool.Clear()`, releasing every sprite's GPU textures while the render context is still alive (see the shutdown-order gotcha below).
- `src/world/worlddefs.h` — **deleted**. Its last two enums, `SoundUniqueId` (`ID_*` sound ids) and `StageFile` (`STAGE_FIRST`/`STAGE_LAST`), followed `SpriteMovingStateHandlers` out to pure Lua (`resources/scripts/soundids.lua`, `resources/scripts/stageids.lua`) once the same zero-remaining-C++-semantics test applied: nothing in C++ ever branched on which specific sound/stage id was which, it just forwarded the value opaquely (`EngineHost::OnCommand`'s song cases straight into `SoundManager`; `LOAD_STAGE_CMD` straight into `LuaEngine::TryDispatchLoadStage`/`on_load_stage`). The one exception, `ID_NO_AUDIO` (a genuine C++-side sentinel meaning "no song currently tracked", checked in `EngineHost::PlaySound`), survives as a local `__SOUND_ID_NO_AUDIO` define in `enginehost.cpp` — nothing in Lua ever names it, so it was never moved.
- `src/lua/` — the entire Lua bridge, one folder matching the `Scarab::Lua`/`Scarab::Engine::Lua` namespace nesting that already existed (this folder used to hold only `luaengine.{h,cpp}`, with the rest sitting in `src/engine/` purely by historical accident — moved here since none of it depends on anything `src/engine/`'s genuinely Lua-agnostic pieces do, see below). `luaengine.{h,cpp}` (`Scarab::Lua::LuaEngine`) is now pure orchestration: it owns the `lua_State`, wires every other class here together from `Init()`/the constructor, and keeps only the handful of methods nothing else reaches (`CallOnUpdate`, `TryDispatchMoveSpritesToScreen`/`TryDispatchLoadStage` — Lua's sole dispatch path for wave-spawn/stage-load queue commands — `GetActiveEnemyCount`, `RunFile`, which prints the actual Lua error message on failure). No longer registers any Caravellius enum as a Lua global — `RegisterEnumsToLuaAsGlobals` was deleted once `SoundUniqueId`/`StageFile` (its last two remaining enums) moved to Lua; `wavestates.lua`/`soundids.lua`/`stageids.lua`/`layerids.lua` self-assign their own ids now. Everything else in this folder is `Scarab::Engine::Lua::*` — one category of Lua-callable primitive per file pair, matching `docs/lua-api/`'s own page split: `LuaScriptingApi` (`sp_wait`/`sp_clear`/`sp_wait_queue_empty`/`sp_move_sprites_to_screen`/`sp_add_label`/`sp_goto_label`/`sp_load_stage` — pure `ScriptProcessor` queue control), `LuaTimerApi` (`set_timer`/`reset_timer`), `LuaSoundApi` (`sound_*` *and*, since both are topically "Sound" even though the song forms reach `EngineHost::OnCommand` through `scriptProcessorPtr` rather than `SoundManager`, the direct/queued song commands: `play_song`/`pause_song`/`stop_song`/`resume_song` and `sp_play_song`/`sp_pause_song`/`sp_stop_song`/`sp_resume_song`), `LuaSpriteApi` (sprite CRUD + `sprite_set_animation_mode` for runtime ANIMATE_LEFT/RIGHT/CENTER switching — the player ship is the only thing that needs this, enemies set their mode once at configure time), `LuaCameraApi`/`LuaInputApi` (incl. `input_add_gamepad`)/`LuaTilemapApi`/`LuaCollisionApi`/`LuaJsonApi`/`LuaAppApi` (app-level concerns not owned by any one subsystem, e.g. `app_set_name`; also `app_set_draw_fps`/`app_get_draw_fps` and `app_set_window_resizeable`/`app_get_window_resizeable`, Phase 5's runtime display toggles), `LuaTextApi` (Phase 8's font/text rendering — `set_font`/`draw_text`/`measure_text`/`screen_get_width`/`screen_get_height`; kept as its own file rather than folded into `LuaAppApi` since text/font is its own subsystem, not a generic app-level concern), and `LuaCollisionListener` (decodes packed handles from `Collider::GetPtrData()` — the sole collision listener in the game now). `LuaEngineUtil` is the shared-helper class every one of these depends on — `GetTileMap`/`GetSoundManager`/`GetSpritePool`/`GetScriptProcessor` (fetch the engine objects stashed as light-userdata Lua globals), `AddOneParmCommandScript` (the shared "queue a one-parameter `ScriptProcessor` command" helper `LuaScriptingApi` and `LuaSoundApi`'s queued song forms both use), `RegisterConstants`, and `s_LuaMutex` — every entry point that touches the shared `lua_State*` (both `LuaEngine`'s own methods above and `LuaTimerApi::SetTimer`'s background-thread callback) is serialized behind this one mutex, because `SunLight::Concurrent::Timer` invokes its callback on its own background thread — see "Known gotchas" below. It lives on `LuaEngineUtil`, not `LuaEngine`, specifically so `LuaTimerApi` (a separate class) can reach it too.
- `src/engine/` — deliberately **not** in the `sunlight` engine repo (see the root `CMakeLists.txt` and sunlight's own `CLAUDE.md` for that boundary). Since the `src/lua/` split above, this now holds only `SpritePool`/`SpriteHandle` (packed generation+index handle pool, `Scarab::Engine::` namespace — no `::Lua` nesting, and neither file includes any Lua header or touches `lua_State`, confirmed before moving everything else out) — the genuinely Lua-agnostic runtime backing for every sprite in the game. `Clear()` immediately destroys every slot, releasing GPU textures; must run before the window/GL context closes, see `EngineHost::OnStop` above.

### Data flow for a stage

1. `resources/scripts/main.lua` runs `Bootstrap.load_sounds()` (reads `resources/configs/soundfile.json` via `load_json`, calls `sound_load` for each entry), dofiles every Lua module, then calls `sp_load_stage(STAGE_FIRST)`.
2. That queues a `LOAD_STAGE_CMD`; `EngineHost::OnCommand` calls `LuaEngine::TryDispatchLoadStage`, which invokes Lua's `on_load_stage(stageId)` (`bootstrap.lua`) — it reads `resources/configs/stagefile.json`, calls `tilemap_load_map(...)`, then `dofile`s the stage's own Lua script (e.g. `1st_stage_corsair.lua`). C++ still owns `ScriptProcessor::Compile()` and the state-machine transition to `STATE_STAGE_RUNNING` afterward (neither is reachable from Lua).
3. The stage's Lua script drives the `ScriptProcessor` command queue — spawning enemy waves via `sp_move_sprites_to_screen(STATE_MOVE_..._TO_SCREEN)`, timing via `sp_wait`/`set_timer`, and music via `sp_play_song`.
4. `EngineHost::OnCommand`'s `MOVE_SPRITES_TO_SCREEN_CMD` case calls `LuaEngine::TryDispatchMoveSpritesToScreen`, which calls the optional Lua global `on_move_sprites_to_screen(stateId)` — every valid wave-spawn state id is claimed by some enemy module's `register_wave_handler`.
5. Enemy/texture/sound parameters (velocity, hit count, textures, explosion/shoot overrides) come from `resources/configs/spriteset.json` and `spritefile.json`, read directly by Lua's `spriteconfig.lua`.

**Adding a new weapon type** (to the player's own weapon track, `weapon.lua`'s `__TRACK`): every weapon must have it's own dedicated `SPRITE_TYPE_*` entry in `resources/configs/spriteset.json` — own `velocity`/`sprite_load_count`/`shoot_sound`/`main_sprite` fields, own dedicated bullet pool constant in `weapon.lua` (`__<NAME>_POOL_TYPE`), and it's own `cfg`/`texturePath`/`sound`/`W`/`H` locals loaded in `Weapon.init()` — the exact same structural pattern BASE/SPREAD/LASER/HOMING already each follow, **even when the new weapon's own bullet is visually/aurally identical to an existing one and could technically just reuse that other weapon's config wholesale.** TWIN (added 2026-08-19) initially skipped this — it silently reused BASE's own `bulletCfg`/`bulletTexturePath`/`__BULLET_POOL_TYPE` for both it's ship shot and it's 2 drone shots, since the bullet really is the same sprite/sound as BASE's — and a same-day follow-up request ("twins should have the same config data structure as any other weapon") fixed it: a new `SPRITE_TYPE_TWIN_BULLET` entry was added (reusing `SPRITE_FILE_CARAVELLIUS_BULLET`/`ID_CARAVELLIUS_SHOOT_AUDIO` - no new art/sound needed, just it's own JSON object) plus it's own `__TWIN_POOL_TYPE`. **Any per-shot tunable that can legitimately differ between a weapon's own emission points (eg. TWIN's drones dealing half the ship's own shot's damage) belongs as a field on that weapon's own config entry (`damage`), not a bare Lua constant** — `spawn_bullet`'s own optional `damage` parameter (defaults to `1`, full damage) is what a weapon's `Weapon.fire` branch passes per-emission-point, read back later via `Weapon.get_damage(handle)` (the same `Enemies.get_damage(otherHandle)` seam every enemy/boss `on_hit` already uses - see the `on_screen_now` gotcha's own neighbor entries below for that mechanism). Same field name (`damage`) as Options' own `SPRITE_TYPE_OPTION_BULLET.damage` (0.5) - keep this name consistent across every future weapon/bullet-owning module too, rather than each inventing it's own (TWIN's own field was briefly called `drone_damage` before being renamed to match, same day). **Don't copy `max_hit_count` onto a new weapon's entry reflexively, though** — unlike `velocity`/`sprite_load_count`/`shoot_sound`/`main_sprite` (all genuinely read for every weapon type, via `probe_texture_size`/`spawn_bullet`/`Weapon.init` itself), `max_hit_count` is only actually consumed by LASER's own fire branch (`laserCfg.max_hit_count`, it's pierce budget) - every other weapon type (BASE/SPREAD/HOMING/TWIN) passes a hardcoded literal `1` for `spawn_bullet`'s `hitCapacity` regardless of what that field says. TWIN's own entry briefly carried an unused `max_hit_count: 1` for exactly this reason (copied reflexively from an existing entry) before it was traced and removed - verify a field is actually *read* somewhere in `weapon.lua` before assuming a new weapon's config entry needs it, rather than copying every field from an existing entry by rote.

**A weapon that needs to temporarily borrow control of another system's own entity** (TWIN combining with real Options, 2026-08-21 - user's own idea: "when you're using twins and get an option a new twin is added perpendicular to other drones... 2 options... forming a format of a cross"): don't have the borrowing module silently reach in and mutate the other system's entity directly - give the owning module (`options.lua`) a single explicit handoff flag per entity instead (`externallyPositioned`, toggled via `Options.set_externally_positioned(handle, bool)`) that it's own update loop checks before writing position, and have the borrowing module (`twin.lua`) set/clear that flag around whatever span it needs control for. This keeps exactly one system ever writing an entity's position at a time without either module needing to know the other's internals, and - critically - means every OTHER concern (firing, damage, collision, eject-on-hit, reset-on-death) keeps working completely unmodified, since none of those care who's currently driving position: `Twin.absorb_option()` calls the ALREADY-EXISTING `Options.add()` to acquire a real satellite handle (changed to return that handle rather than a bare `true`, confirmed backwards-compatible since no existing call site checked the old return value) and marks it externally-positioned; `Twin.deactivate()` (reached via `Weapon.demote()` on a hit, BEFORE `Options.eject()` - the two-step ordering itself is what makes this work with no new eject logic) just clears the flag, handing the satellite straight back to Options' own normal Gradius-trailing with zero special-casing on Options' side. Only position is ever handed off - `Options.fire()`/`Options.get_damage()`/`Options.eject()` all read a satellite by it's handle exactly the same regardless of this flag, and a module reading/writing an unrelated per-entity concern (here, the ship-lean pose-sync) can and should keep running unconditionally on every entity - it's harmless/idempotent and orthogonal to whichever system currently owns position, so it doesn't need it's own copy of this same borrow/return dance. See `twin.lua`'s own header comment for TWIN's exact slot layout (0°/180° fixed to it's own 2 built-in drones, 90°/270° filled one at a time by absorbed Options) and `options.lua`'s `Options.update`/`Options.set_externally_positioned` for the owning side.

**Adding a new enemy type** (or changing an existing one): everything is Lua. Add/change a `resources/scripts/enemies/<type>.lua` module (following the shape of the existing ones — `common.lua`'s `Enemies` registry for update/collision/wave-spawn dispatch, `spriteconfig.lua` for velocity/hit-count/texture/sound config, `movement.lua`/`shooting.lua` for shared math, `resources/scripts/bullets/*.lua` for shared bullet pools), plus config entries in `resources/configs/spriteset.json`/`spritefile.json`/`sprite-moving-parms.json` and a new `STATE_MOVE_*` name in `resources/scripts/wavestates.lua` for each new wave-spawn state. No C++ changes needed. **Also call `sprite_set_collision_inset(handle, __COLLISION_INSET_X, __COLLISION_INSET_Y, __COLLISION_INSET_X, __COLLISION_INSET_Y)` right alongside the module's own `SpriteConfig.configure_ship_textures(handle, cfg)` call** — every regular enemy (satellite/cylinder/alien/octopus/ufo/galileo/nomad) does this as of 2026-08-18, using the exact same fraction-based values as the player ship's own `__COLLISION_INSET_X`/`_Y` (`player.lua`, `0.15`/`0.10`) as a project-wide default, applied uniformly rather than tuned per type — a new regular enemy should follow that same default unless there's a specific, art-driven reason to differ. `sprite_set_collision_inset`'s percentages are fractions (0.0-1.0) of the sprite's own *current* width/height, recomputed on every collision check — never hardcoded pixels — so this stays correct even if the active sequence's size later changes; see `LuaSpriteApi::SetCollisionInset`'s own doc comment (`src/lua/luaspriteapi.cpp`) for the mechanism, and `Bootstrap.setup_collision_rules`'s own comment (`bootstrap.lua`) for a real, separate gotcha about collision-rule argument order silently dropping one side's inset. A boss/sub-boss with irregular per-part art (Cephalon's head/arms, the Venusian sub-boss) instead tunes it's own dedicated inset constants by eye against that part's real silhouette, rather than reusing this shared default — leave those as-is, this default is specifically for regular wave-spawn enemies. **Any enemy that shoots must gate it's shoot trigger on a `fully_on_screen` check (the whole sprite's bounding box within the viewport), never on a generous origin-only `on_screen_now`-style check alone** — see the `on_screen_now`/rearm-mechanic gotcha below for the full mechanism and why this is easy to get wrong by copying an existing module's own despawn check verbatim into the shoot gate too. As of 2026-08-20 every shooting enemy (satellite doesn't shoot; cylinder/alien/octopus/ufo/galileo/nomad all do) has this fix - a new shooting enemy module should follow the exact same `fully_on_screen` pattern from the start, not add it later once a live playtest catches "shooting with no ships visible" again. **A regular (wave-spawn-based) enemy needs no new debug plumbing at all** — `resources/scripts/debug/enemy_main.lua`'s generic harness already covers it the moment it's registered; just point `DEBUG_ENEMY_STATE_NAME` at the new `STATE_MOVE_*` name to test it in isolation. A **boss/sub-boss with it's own non-wave-spawn trigger** (self-triggering off some other condition, the way the Venusian sub-boss self-triggers off `camera_get_position()` rather than a wave state) needs it's own dedicated debug launcher pair instead — copy `resources/scripts/debug/subboss_main.lua`/`subboss_stage.lua` as the template (new `STAGE_DEBUG_<NAME>` id in `stageids.lua`/`bootstrap.lua`'s `STAGE_ID_TO_NAME`/`stagefile.json`, a debug stage script that sets up whatever makes the new encounter trigger quickly and loops on resolution) — see `resources/scripts/debug/`'s own header comments for the full mechanism. A boss with **several independently-collidable parts** (Cephalon's head + two arms, `resources/scripts/enemies/cephalon.lua`) may also want a debug-only global the boss module itself reads (see `DEBUG_CEPHALON_DISABLE_ATTACKS`, checked directly in `cephalon.lua`) to isolate one part from the rest for precise hitbox/behavior tuning, beyond what camera/trigger tricks in the launcher alone can do; and a feature that depends on real stage context rather than isolation (Cephalon's own stage-BGM-crossfade, which needs the actual stage track's real loop-cue timing playing first) may want a *third* kind of debug launcher that deliberately plays real stage setup rather than reusing the isolated boss-only stage — see `resources/scripts/debug/cephalon_realstage_main.lua`/`cephalon_realstage_stage.lua`'s own header comment for why it does NOT just `dofile` the real stage script wholesale (jumping the camera close to a late-stage trigger mark lands past any earlier mid-stage trigger marks too, and those have no "already passed" memory, so they'd fire unexpectedly).

### Lua migration (complete, all 9 phases — `feat/lua-refactor` branch)

A refactor moved all enemy/sprite/player game logic and config/stage bootstrap out of C++ and into Lua, then deleted the C++ that became dead as a result, leaving C++ as a thin, reusable, game-agnostic engine layer (see `src/lua/`/`src/engine/` above). Every phase of the original 9-phase plan is done: Satellite, Cylinder, Alien, Octopus, Ufo, Galileo, Nomad, the player ship (`player.lua`), config/stage loading (`spriteconfig.lua`/`bootstrap.lua`), and (Phase 9) the bulk deletion of `src/config/`, `src/sprite/spritemoveprocessing.{h,cpp}`, the legacy sprite queues and collision listener that used to live in a separate `WorldBase` class (since merged into `EngineHost`, see below), and `EngineHost`'s config/stage/input/move-to-screen methods.

Enemy migrations were self-contained vertical slices — the old C++ path for a type wasn't touched, it just went dead (unreferenced but still compiled) once its Lua module claimed the dispatch, until Phase 9 deleted it. The player ship and the config/stage bootstrap were **not** vertical-sliced this way — both are singular, non-per-type mechanisms where the old and new paths can't coexist (e.g. C++ input handlers and Lua polling would both drive the same physical ship), so those were full switch-overs: implement the Lua side, verify it works, then unwire the old C++ call sites in the same change (with the dead bodies deleted later, in Phase 9).

- `resources/scripts/spriteconfig.lua` — generic reader over `spriteset.json`/`spritefile.json` (via `load_json`) that every enemy module and `player.lua` use for velocity/max-hit-count/texture-setup/sound-ids, replacing what used to be hardcoded Lua literals kept in sync with the JSON by hand.
- `resources/scripts/bootstrap.lua` — sound loading (`soundfile.json`) and the `on_load_stage(stageId)` hook (`stagefile.json` + `tilemap_load_map` + `dofile`) described above.
- `resources/scripts/player.lua` — the player ship: movement (keyboard + gamepad button *and* left-analog-stick with deadzone), shooting, and hit/explosion/blink, all via the same generic sprite pool/collision primitives every enemy uses.
- `resources/scripts/enemies/` — the enemy-side modules:
  - `common.lua` — the shared `Enemies` registry (`register_update`, `claim`/`release` for collision dispatch, `register_wave_handler`, `register_count`) so each module can hook the single global `on_update`/`collision_set_handler`/`on_move_sprites_to_screen` slots without clobbering each other. Also `get_active_enemy_count` (feeds `EngineHost::CheckSpritesQueueEmpty`) and the `collision_set_handler` callback that mirrors the old mutual-immunity check (see gotchas below).
  - `movement.lua` — shared sine/straight-line/vertical-sine movement math and viewport-bounds computation.
  - `shooting.lua` — shared shoot-height threshold + periodic (not per-bullet) reload sweep.
  - `satellite.lua`, `cylinder.lua`, `alien.lua`, `octopus.lua`, `ufo.lua`, `galileo.lua`, `nomad.lua` — the per-type modules themselves.
- `resources/scripts/bullets/` — shared bullet-pool modules, not tied to any one enemy type (each is reused across whichever modules need that projectile shape): `linebullets.lua` (straight-line) / `seekerbullets.lua` (Bresenham seeker) pools. Kept out of `resources/scripts/enemies/` specifically because they're generic projectile primitives, not enemy behavior — mirrors how `resources/scripts/core/` already holds shared systems that aren't per-enemy either.
- `resources/scripts/debug/` — standing debug-only launch sessions for testing enemies/bosses/sub-bosses in isolation during development, each a plain `argv[1]` entry point (`./scarab resources/scripts/debug/<name>_main.lua` — `EngineHost::ResolveEntryScript` accepts a bare `.lua` path, no `project.json` needed) that sets `DEBUG_ENTRY_STAGE_ID_NAME` before `dofile`-ing the real `main.lua` completely unchanged, so full normal bootstrap runs and production itself is never touched — `main.lua`'s own final `sp_load_stage` and `gameover.lua`'s `restart_game()` both check that global before falling back to `STAGE_FIRST` as always. `enemy_main.lua`/`enemy_stage.lua` is the generic one covering every regular wave-spawn enemy (see the "Adding a new enemy type" note above); `subboss_main.lua`/`subboss_stage.lua` is the Venusian sub-boss's own dedicated one, and the template for any future boss/sub-boss with it's own non-wave-spawn trigger. `cephalon_main.lua`/`cephalon_stage.lua` follows that same template for the Phase 4 final boss, plus two further variants built once the base template wasn't enough on it's own: `cephalon_collider_test_main.lua` (sets `DEBUG_CEPHALON_DISABLE_ATTACKS`, a debug-only global `cephalon.lua` itself reads to freeze/hide/decollide the arms for isolated head-hitbox testing) and `cephalon_realstage_main.lua`/`cephalon_realstage_stage.lua` (plays the real stage's own BGM/background rather than isolating completely, for testing things — like a stage-BGM crossfade — that depend on real stage context; see it's own header comment for why it deliberately doesn't just `dofile` the real stage script wholesale). Kept as it's own top-level folder (not under `enemies/`) since it's development tooling, not game content — and note `.gitignore`'s `**/debug/` rule (aimed at stray CMake `Debug`/`Release` build-output dirs) has a targeted negation for this specific path; don't assume every `debug`-named folder added later is automatically trackable without checking that.

## Code style (existing convention — match it, don't "fix" it)

- Scope resolution operator is always **space-padded**: `Scarab :: Host :: EngineHost`, `SunLight :: Renderer :: TileMapRenderer`, not `Scarab::Host::EngineHost`.
- Member functions/types: PascalCase (`RunStageStateHandler`, `LuaEngine`). Member variables: `m_` prefix + Hungarian-ish tags (`m_nCenterWidth` = int, `m_pMainSpritePos` = pointer, `m_str...` = string, `m_bOverride...` = bool). This convention is C++-only — `resources/configs/*.json` field names are plain snake_case with no type prefix (`velocity`, `sprite_load_count`, `main_sprite`, ...), matching the snake_case already used for every Lua-callable primitive (`sprite_configure_texture`, `tilemap_load_map`); the config files originally carried the C++ Hungarian names verbatim (`m_nVelocity`, `m_strFileName`, ...) as a leftover of the old hand-written-struct `Config` reader, cleaned up once `load_json`/`spriteconfig.lua` made the JSON schema itself Lua-facing.
- Struct-of-data types are prefixed `st`. Enums are UPPER_SNAKE with a type-prefixed member name (`SPRITE_MODE_CIRCULAR`) and end with a `_LAST` (and sometimes `_UNLISTED`) sentinel — keep sentinels last when extending. Watch for a sentinel that doubles as a real value (see the `STAGE_LAST` gotcha below) before assuming an id-assignment loop's bound should be exclusive.
- Doxygen-style `/** @brief ... */` comments precede non-trivial methods; this repo does use them (unlike the terser default) — follow the existing pattern when touching documented methods, but don't add commentary the surrounding code doesn't already have.
- No magic numbers, project-wide (not just movement math, and not just Lua) — every numeric/string literal that means something gets a named constant, with a comment where the value itself needs explaining (derivation, tuning history, `-- matches __UFO_SHIP_STEP`-style pointers back to an original C++ name where relevant).
- Every Lua module's own **module-level constant** (a `local` declared at the top level of the file, assigned once and never reassigned — pool-type strings, durations, thresholds, fractions, phase/state name constants, sequence indices, lookup tables built once and read-only afterward, ...) is prefixed `__` (`local __POOL_TYPE = "cephalon_head"`, `local __ARM_MAX_SEGMENTS = 12`), mirroring the old C++ `#define` naming this repo's Lua ports already reference in comments. This is a real, swept-and-verified convention as of 2026-08-11 (every `resources/scripts/**/*.lua` file), not just a stage-script quirk — apply it to any new module-level constant in any file. It does **not** apply to: genuinely mutable per-frame/per-hit state (`ships`/`bullets`/`arms`-style handle-keyed registries, state-machine variables, elapsed-time counters), config caches forward-declared with no initializer and populated once at `.init()` time from JSON (`local SHIP_VELOCITY` then `SHIP_VELOCITY = cfg.velocity` later), or a module's own exported table (`local Cephalon = {}`) — only genuine, immediately-initialized, never-reassigned module-scope locals. `Movement.*`/`Enemies.*`-style constants attached directly as fields on an exported table (not `local` at all) are out of scope too — there's nothing to prefix.

## Known gotchas

- `SunLight::Input::KeyboardKey` vs raylib's own global `KeyboardKey` is a real footgun in engine code (see sunlight's own `CLAUDE.md`) — always fully qualify if you touch input handling.
- The `SPRITE_MODE_SINE_*_FAST` cases use `STEP_360 * RADS_180`, while `*_SLOW` uses `STEP_180 * RADS_360` (`movement.lua`) — easy to transcribe backwards (it was, independently, in two different Lua ports before `movement.lua` consolidated the fix) since the constants look superficially similar; FAST should oscillate roughly 4x faster than SLOW.
- `stCoordinate2D`/sprite position is top-left anchored, not center-anchored (confirmed via both the render clip rect and the AABB collision code in the original C++) — a formula like `pos - height/2` doesn't mean "half a sprite-height above center", it means "half a sprite-height above the sprite's own top edge". Worth checking against before assuming any position math matches visual intuition.
- `SunLight::Concurrent::Timer::Start()` runs it's callback on it's own background thread; `lua_State` isn't thread-safe, so any code calling into Lua from both the main thread and a timer callback needs to serialize via a mutex (see `LuaEngineUtil::s_LuaMutex` — lives there, not on `LuaEngine`, since `LuaTimerApi::SetTimer`'s background-thread callback needs it too). Watch for deadlock if a mutex-holding call can trigger `Timer::Stop()` (which `std::thread::join()`s) — the timer thread must not block on the same mutex, or a `join()` from the mutex-holding thread deadlocks against it (fixed via `try_lock` in the timer callback rather than a blocking lock).
- **`s_LuaMutex` only protects the shared `lua_State*` itself — it does NOT protect `EngineHost`/`SoundManager`/raylib's own audio/engine state, which the main thread also touches every frame outside that lock.** A `set_timer` callback (background thread) that calls any Lua primitive reaching into that state — `play_song`/`sound_is_playing` (→ `SoundManager`/raylib directly), any `LuaSoundApi::CallPlayCommandDirect`-style call (→ `EngineHost::OnCommand`, touching `m_CurrentSong` etc.) — races the main thread's own identical access with zero synchronization, a real bug found live (2026-08-18) in `bgm.lua`'s old `on_tick`: it called `sound_is_playing`/`play_song` directly from the Timer's background thread every second, which could corrupt state or hang the whole game if it landed inside a raylib/miniaudio-internal lock (reported as "scarab got frozen" mid-playtest, confirmed via VSCode's debugger stopping at `luatimerapi.cpp`'s `lua_pcall` call site). **Rule for any `set_timer` callback, if this codebase ever uses one again**: it may only ever touch plain Lua data (safe under `s_LuaMutex`, which is all that mutex actually guarantees) — never call a primitive that reaches `EngineHost`, `SoundManager`, `SpritePool`, or any other engine-owned C++ object from inside one; flip a plain boolean flag instead and let a separate `Enemies.register_update`-driven function read/act on it the next real frame. `bgm.lua` no longer uses `set_timer` at all as of it's final redesign (see the next gotcha entry) - this rule is preserved for whenever a future case genuinely needs a background-thread timer, not because any live example of the pattern exists in this codebase today (checked project-wide, 2026-08-18: `set_timer`/`reset_timer` are used nowhere).
- **`dt`, as passed to every Lua `on_update`/`Enemies.register_update` callback, is NOT a real measured frame time — it's a fixed `#define __FRAME_DELTA_MILLI (1000 / 60)` (`enginehost.cpp`), and that's *integer* division, truncating to `16`, not even the true `16.666...`.** Any Lua-side counter that accumulates `dt` to track real elapsed time (a timeout, a cooldown meant to correspond to real seconds) silently drifts slow against real wall-clock time by design — roughly 40ms slow per real second (~4%) from the truncation alone, compounding forever with no self-correction, and gets *worse* under real frame-rate variance (a slow frame that actually took 50ms of wall-clock time is still reported as exactly 16ms of `dt`, that difference is simply invisible to Lua). Found live, 2026-08-18, across two failed attempts at `bgm.lua`'s own loop-cue timer before landing on the fix below: first a `dt`-accumulator design was audibly late within a single song's loop cycle (this `dt` truncation), then a `set_timer` + flag-handoff redesign (real OS-timed ticks, see the previous gotcha entry) was *still* audibly late, because the underlying whole-second counting it drove bounded the timing error rather than eliminating it. **The actual fix, landed (`d58eeb6`): stop using `dt`/counting/any timer at all for this - compare Lua's own `os.time()` (real wall-clock seconds since epoch, part of Lua's standard library, confirmed available in this build via a live test) against a start timestamp directly, every frame.** No accumulation error at all, since each check is against absolute real time rather than a running sum of approximations - and since there's no background thread involved, the whole cross-thread safety concern from the previous gotcha entry doesn't even apply. See `bgm.lua`'s own header comment for the full three-design history. `dt` itself remains fine for what most of this codebase already uses it for (short, gameplay-feel timings - explosion/blink timers, `HOMING`'s turn-rate steering, `Pickups.eject`'s grow/circle duration - where a few percent of drift over a couple of seconds is imperceptible); `os.time()` is specifically the better tool for anything tracking real elapsed time over a long, continuous duration.
- **"Resources-only" (Lua/JSON/sprite, no `.cpp` touched) is not the same as "no rebuild needed" — a plain relaunch of `build/scarab` without running `cmake --build build` first replays whatever was copied into `build/resources/` on the *last* build, not the source tree's current state.** `caravellius_copy_resources` (see the Build section above) only re-copies as part of a real build invocation; skipping that step and just re-running the already-built executable silently tests stale code with zero error or warning — the game just behaves exactly as it did before the edit. Real live mistake, 2026-08-19: a genuine bug fix (Options/satellites' pose-sync, see the `sprite_set_active_sequence` gotcha below) was edited into `options.lua`, then tested via a direct relaunch with no rebuild in between — the user re-tested and reported "still not [working]", which looked like the fix itself was wrong, when the actual problem was that the *old* code was still what was running (`diff`ing `games/caravellius/resources/...` against `build/resources/...` confirmed the mismatch). **Always run `cmake --build build -j 4` before any test relaunch, even for a pure Lua/JSON/sprite edit with zero C++ changes** — it's fast (nothing needing recompilation is rebuilt) and the resource-copy custom targets have no way to be "skipped safely."
- **`sprite_set_active_sequence(handle, sequenceId)` unconditionally resets the target sequence's own animation state**, even when it's already the active sequence — confirmed via sunlight's own source (`Sprite::SetActiveTextureSequence`, `build/_deps/sunlight-src/src/sprite/sprite.cpp`) unconditionally calling `Reset()` on the newly-selected sequence's `TextureCanvas`. Calling this every frame regardless of whether the sequence actually changed (found live building Options/satellites' pose-sync, 2026-08-19 — see `options.lua`'s own header comment) silently freezes any `AUTOMATIC_CIRCULAR`/`AUTOMATIC_RIGHT_LEFT` animation on that sequence at it's first frame forever, since the reset undoes each frame's own advance before it's ever drawn. Always track the last sequence actually set (per-sprite, e.g. a `lastLeanIndex`-style field) and only call this again when it genuinely changes. Full primitive doc + the worked pose-following pattern this bug came from (a follower sprite tracking another sprite's real-time animated pose with no new C++ primitive, since nothing exposes a sequence's currently-animating tile back to Lua) are in `docs/lua-api/sprite.md`.
- Acquiring/positioning/`sprite_add_to_layer`-ing a sprite from a Lua module's `init()` fails silently and leaves it invisible, if `init()` runs before the map is actually loaded — `main.lua`'s `dofile`/`init()` calls all happen synchronously *before* `sp_load_stage`'s queued `LOAD_STAGE_CMD` has run `LoadMap` (that only happens on the first `STATE_STAGE_RUNNING` tick). Every enemy module sidesteps this by only ever acquiring/adding sprites from a wave-spawn handler triggered later by the stage script; `player.lua` has no such natural trigger, so it defers real spawn to the first `Player.update()` call instead (see it's own comments).
- The player's original C++ shoot cooldown (now ported faithfully in `player.lua`) stamps it's "last shot" timestamp on *every* poll, not just when a bullet actually fires — since it's polled every render frame while the key is held, this means holding the key down only ever fires once (the ~16ms per-frame gap never exceeds the cooldown threshold again), and only releasing/re-pressing fires again. Looks like a bug but is what gives the felt semi-auto rate limit; a version that only stamps the timestamp on an actual shot produces true full-auto instead (reported during this refactor as "machine gun").
- `player.lua` drives movement from *both* the physical gamepad D-pad buttons *and* the left analog stick (translated to virtual D-pad presses with a 0.1 deadzone, matching the original C++'s `TileMapRenderer::HandleUserInput`) — polling only `input_is_gamepad_button_down` misses stick-only controllers entirely; also poll `input_get_gamepad_axis` with the same deadzone.
- The pure-Lua `collision_set_handler` (`common.lua`) must OR immunity across *both* colliding sides (skip the whole collision if either side is already exploding/blinking) — without it, two sprites overlapping for several consecutive frames (e.g. the player ramming a multi-hit enemy) re-trigger `on_hit` on the not-yet-maxed side every one of those frames, racking up it's full hit count within a single touch instead of requiring separate encounters over time.
- The old C++ `RegisterEnumsToLuaAsGlobals`'s per-enum registration loops assumed every `*_LAST` sentinel was a pure bound never used as a real value — true for `SoundUniqueId`, but **not** for `StageFile::STAGE_LAST`, which doubled as an actual, loadable stage id (real `stagefile.json` entry); that loop needed a `<=`, not a `<`, and it was a real bug the first time Lua code needed to reference `STAGE_LAST` by name. `RegisterEnumsToLuaAsGlobals` no longer exists (both enums moved to `resources/scripts/stageids.lua`/`soundids.lua`), but `stageids.lua`'s own comment preserves the reasoning: `STAGE_LAST` still gets defined identically to every other id there, since Lua's flat `define()` calls have no bound to get backwards in the first place.
- `CMAKE_CXX_STANDARD 17` must be set **unconditionally** in the root `CMakeLists.txt`, not gated behind `if(APPLE)` — it originally was (added only for some Apple-specific raylib defines, long before this repo used `std::filesystem`). That meant Linux/GCC and Windows/MSVC builds never got an explicit standard flag and silently fell back to each compiler's own default, which can be pre-C++17 — breaking `std::filesystem` (`enginehost.cpp`'s `ResolveEntryScript`) with a confusing compile error instead of a clear "wrong standard" message. Found by actually building on Linux, not by code review — a macOS-only compile gives zero signal here. `CMAKE_CXX_STANDARD_REQUIRED ON` is set alongside it so an incompatible compiler hard-errors instead of silently downgrading again in the future.
- `EngineHost::OnStop()` must release `SpritePool`'s textures (`m_SpritePool.Clear()`) — it can't be a no-op. `TileMapRenderer::Stop()` (sunlight) calls every listener's `OnStop()` *before* `CloseWindow()` tears down the GL context, specifically so listeners get a chance to free GPU resources while the context is still valid; `EngineHost` didn't use that hook for a while, so `SpritePool`'s textures instead got released later, by `~SpritePool()` at program exit — *after* the context was already gone. `TextureCanvas`'s destructor calling into raylib to unload a texture at that point segfaults (`rlUnloadTexture`). Symptom looks exactly like a random exit-time crash (e.g. via ESC) with no connection to whatever gameplay code was touched most recently — check `OnStop()`/shutdown ordering before assuming an exit crash is caused by recent gameplay changes.
- `sprite_set_pos(handle, x, y)`'s C++ binding (`LuaSpriteApi::SetPos`) reads `x`/`y` via `lua_tointeger`, which **silently fails on a genuinely fractional float** (writes 0, doesn't truncate) rather than rounding/truncating it. Every existing call site already wraps it's own coordinates in `Movement.trunc(...)` for exactly this reason — a new call site that skips it (found live building Cephalon's head roam movement, `resources/scripts/enemies/cephalon.lua`) doesn't error or warn, it just makes the sprite appear to silently stop moving partway (every other frame's write fails, leaving the position wherever the last successful *integer* write left it) — a confusing, hard-to-diagnose symptom with no exception or log line pointing at the cause. Always `Movement.trunc()` (or equivalent) any position math before `sprite_set_pos`, even values that "shouldn't" end up fractional (e.g. an integer base plus a `1.5`-per-frame velocity).
- `sunlight`'s `CollisionManager::Update()` only honored the *first*-registered collider's own `Collider::SetInset` for a `collision_add_rule(A, B)` pair — fixed upstream in `v0.7.0` (see [[reference_sunlight_cross_repo_workflow]] for the full story), but the underlying class of bug is worth remembering for any future two-sided check in this codebase: a symmetric-looking API (`SetInset` exists identically on both sides of a collision pair) doesn't guarantee a symmetric-looking *call site* actually exercises both sides — `pFirst->Hit(pSecond->GetDimension2D())` only ever looked "two-sided" at a glance. Went unnoticed for an entire sunlight release cycle because no enemy in this game called `sprite_set_collision_inset` at all until Cephalon did — a feature can compile, pass review, and sit unexercised long enough that a real bug in it reads as "brand new" when it's actually as old as the feature itself.
- A "still on screen" boundary check that's correct for one purpose isn't automatically correct for another — every shooting enemy's `on_screen_now` (only tests a sprite's *origin corner* against the viewport boundary, ignoring its own width/height) is deliberately generous, which is exactly right for despawn timing (don't drop a ship until every last pixel is gone), but was also reused, incorrectly, as the shoot-eligibility gate. Combined with the rearm mechanic (`shooting.lua`'s periodic sweep clears `has_shot` regardless of a ship's current position, and the shoot threshold itself — an absolute Y position, or Galileo's own "distance traveled since entering screen" — is already trivially satisfied by the time a ship rearms, since it necessarily crossed that threshold once already to earn its first shot) this let ships fire while the majority of their own sprite had already exited the visible area. First found in `galileo.lua` (confirmed live, the last ship of a wave firing from ~62% off-screen, reported as "shooting with no ships visible") and fixed there alone at the time. **A 2026-08-20 project-wide sweep (prompted by the user asking "maybe any other enemy?") found the exact same unfixed vulnerability copy-pasted into every other shooting enemy module** — confirmed live via the same diagnostic-logging method, before touching any code: `octopus.lua` fired off-screen 5 of 28 test shots (up to ~75% of the sprite below the visible bottom edge), `nomad.lua` 2 of 36, `ufo.lua` 1 of 16; `cylinder.lua`/`alien.lua` share the identical vulnerable code but didn't trigger it in that particular sample window (not evidence of immunity, just luck of the timing). All 5 fixed the same way as Galileo — a `fully_on_screen` check (the *whole* sprite's bounding box within bounds, not just it's origin) gating the shoot trigger specifically, with despawn timing left on the original generous `on_screen_now` check, which is correct for that purpose. Re-verified live after the fix: 0 off-screen shots across every previously-confirmed-vulnerable type. Watch for this same "one generous flag reused for two purposes with different correctness needs" shape in any future gating logic — and see the "Adding a new enemy type" note above for the standing rule this created.
- `screen_get_width`/`screen_get_height` (Phase 8, `LuaTextApi`) return the engine's **fixed design/render resolution** (`DISPLAY_W`/`DISPLAY_H` in `main.h`, `1260x920` today) — the coordinate space `draw_text` and every other screen-space draw call (the FPS counter, the screen-fade overlay) actually operate in. This is deliberately **not** the live, resizeable OS window size (`app_get_fullscreen`/Phase 5's window-resizeable toggle both change that independently) — the engine always letterbox-scales the fixed resolution to fit whatever the real window size ends up being, so HUD layout math (e.g. `hud.lua`'s right-aligned lives counter) must measure against `screen_get_width()`, not anything that varies with the actual window. Getting this backwards wouldn't error, just silently misplace on-screen text the moment the window is resized or fullscreen is toggled.
- `set_font(path)`'s underlying raylib call (`RaylibEngine::SetFont`) auto-detects the font file's format purely by extension — `.ttf`/`.otf` via stb_truetype, `.fnt` via raylib's own AngelCode BMFont loader — so nothing in this codebase (`LuaTextApi`, `ITileMap`, `IEngine`) has any format-specific logic of its own, and none of it will need to change if a bitmap font ever replaces the current pixel TTFs (`games/caravellius/resources/fonts/msx-screen0.ttf`, set from `main.lua`). A bad/missing path fails gracefully (`set_font` returns `false`, the previously active font — including the engine's own built-in default, if `set_font` was never called successfully — stays in effect); it does not error or crash.
- `play_song(id)` (direct/immediate dispatch) does **not** mark a song as the auto-relooping "currently tracked BGM" — only the queued `sp_play_song(id)` does, since `EngineHost::OnCommand`'s `PLAY_SONG_CMD` case sets `m_CurrentSong` before falling through into the shared body `PLAY_SONG_DIRECT_CMD` also uses; `PLAY_SONG_DIRECT_CMD` alone never sets it. `EngineHost::RunScriptMachine`'s per-frame `PlaySound(m_CurrentSong)` is what gives a tracked song it's free looping (raylib's `Sound` has no native loop support) — a song started via plain `play_song` therefore plays exactly once through it's own real length and then goes **permanently silent**, with no error or log line pointing at why. Found live: Cephalon's boss BGM (`cephalon.lua`, started via `play_song` specifically to bypass a possibly-queue-stuck `sp_play_song`, same reasoning `bgm.lua`'s own header comment gives for `stop_song`/etc.'s direct forms) went silent ~170s into any fight that ran that long. Fixed with a new primitive, `play_song_looping(id)` (`LuaSoundApi::PlaySongLooping`) — dispatches immediately like `play_song`, but reuses the existing `PLAY_SONG_CMD` enum value (not a new one) so it *also* sets `m_CurrentSong`, giving both immediacy and looping together; use it (not plain `play_song`) for any BGM that must start outside the queue. Verified live both ways: broken run showed `sound_is_playing` going `false` at ~170s and staying `false`; fixed run showed it still `true` at 180s (7s past the song's own real length — only possible if it actually looped). See `docs/lua-api/sound.md`'s own "queued vs. direct" table for the full 3-way primitive comparison, and `resources/scripts/core/bgmregistry.lua`/`soundfile.json`'s `duration_seconds`/`loop_cue_lead_seconds`/`loop_cue_song_id` fields for how a looping BGM's own real-world timing is now centralized (measured once via `afinfo <file>`, entered as JSON data) rather than hand-duplicated as local constants in every file that plays that song.
- `Scarab::Engine::SpritePool::Release()` (`src/engine/spritepool.cpp`) **must never clear `stSlot::nativeTextureWidth`/`nativeTextureHeight`** — a change that did (commit `938f3c7`, landed and reverted the same day, `039741c`) looks like a reasonable stale-cache fix but is actually removing a load-bearing workaround for a genuine sunlight behavior, confirmed by reading sunlight's own source directly (not guessed): `TextureCanvas::Load()` (`canvas/texturecanvas.cpp`) only writes a freshly-loaded texture's real dimensions into it's own dimension struct if that struct is currently `(0,0)` — true only the *first* time a given `TextureCanvas` C++ object is ever loaded; `Sprite::AddTextureSequence` (`sprite/sprite.cpp`) then permanently repoints that same canvas's dimension pointer (`GraphicObject::SetDimension2DPtr`) at the owning `Sprite`'s *shared* dimension struct, which subsequently holds the sprite's *tile* size (native width / frame count), not the texture's native size. Since `SpritePool` reuses the same `TextureCanvas` objects across every `Release()`/`Acquire()` cycle (never destroyed, only unloaded/reloaded), a slot's second-and-later configure hits `Load()`'s now-false guard and silently reads back it's own *previous life's tile size* as if it were the texture's native width — reproduced live across every enemy type, not just one (e.g. Cylinder's real 128px native width reads back as 32 = 128/4 frames on recycle), each time diagnosed as "cropped/partial" or wrongly-sized sprites with zero error/log line pointing at the cause. `GetOrCacheNativeWidth`/`GetOrCacheNativeHeight` caching the *first* (genuinely reliable) native size forever, and ignoring what every later reconfigure's now-aliased `GetDimension2D()` reports, is the correct and permanent fix for this — not a bug to "clean up" later. Full mechanism writeup lives in `Release()`'s own comment (also explains the narrower, already-solved case this cache also covers: a pool shared across multiple differently-sized textures, worked around in `games/caravellius/resources/scripts/core/weapon.lua` via one dedicated pool per weapon-bullet texture).
- **A layer's own `visible` flag in the `.tmx` gates every runtime sprite registered against that layer id too, not just it's static tile/object content — parent-child visibility, by design (fixed 2026-08-26).** Found while building Phase 10.1's storyboard: sunlight's `TileMapRenderer::DrawAllLayers` is the only path to `HandleSpriteUpdate` (the call that actually draws a sprite), and it used to only fire from the tile-layer (`L_LAYER`) branch, never the objectgroup (`L_OBJGR`) one — meaning every "(Empty)" placeholder sprite layer this project uses (`LAYER_ENEMIES_SHIPS`/`_BULLETS`/`_PICKUPS`/`_PLAYER_OPTIONS`/`_STORYBOARD`, all objectgroups) never actually drew it's sprites at all, full stop, regardless of the layer's own `visible` value — confirmed live via direct instrumentation of the engine's own render loop, not assumed: only the player ship (which reuses the one real, visible tile layer) ever rendered. Fixed upstream in sunlight by moving the `HandleSpriteUpdate` call to one site in `DrawAllLayers`, called for every layer type but still gated on `pLayer->visible` — restoring a clean parent-child hierarchy (a sprite's own `sprite_set_visible` only ever gets a say once it's container layer is itself visible). **Direct, load-bearing consequence for every map in this game**: every placeholder sprite layer must now be authored genuinely visible (`visible="1"`, or the attribute omitted) — `MAP_AUTHORING.md`'s own convention was `visible="0"` before this fix, which is now exactly backwards. To hide a whole layer's sprites at runtime as a group, use `tilemap_set_layer(layerId, false, ...)` (already exposed to Lua) rather than authoring the layer invisible from the start. See [[reference_sunlight_cross_repo_workflow]] for the full fix/verification story.
